## 2026-09-05 — full text of live triggers compressed in STATE.md (size pass)

**Three accepted auth exposures (TASK-0003).** (a) The Data Protection key ring is unpersisted, so
a restart or a second replica issues 403s against outstanding CSRF cookies — invisible with one
long-lived process, immediate on any real deployment or scale-out. Trigger: deployment (Open
question 5). (b) The bootstrap CLI prints the temporary password to stdout, so it lands in shell
history and any terminal capture. (c) `PersistLockoutStateAsync` opens a DbContext only on the
account-exists path, a timing asymmetry an attacker could use to distinguish a known email from an
unknown one — narrower than the Argon2id-verify asymmetry spec 6.1.11 addresses, but the same
class. Owner `backend-dev`.

**`SameSite=Lax` on both auth cookies assumes frontend and API share a registrable domain**
(TASK-0003 approved delta). If they end up cross-site, `Lax` silently stops sending the session
cookie on the requests that matter; the fix is `SameSite=None; Secure` PLUS a reconsidered CSRF
posture, because the double-submit pattern's threat model changes cross-site. Not a one-line
tweak, and it must be decided WITH the deployment topology, not after. Trigger: Open question 5.
Owner human + `backend-dev`.

**The Api→Infrastructure architecture test exempts `StartupEnvironmentGuard` as well as
`Program.cs`.** The guard reads `DatabaseOptions` at `StartAsync`. Two exemptions is a judgement
call; three is a rule eroding one name at a time. Trigger: a THIRD exemption must argue for itself
or the type gets a port.

**No `Idempotency-Key` mechanism.** §6 and spec §9.8.2 require it; deferred as Option B with human
sign-off on 2026-09-04, full record in `backend/docs/ASSUMPTIONS.md` §2.14 and this file's

## 2026-09-15 (TASK-0062) — three gaps declared by the implementing agent, all accepted

All three were **declared in the agent's own report, not found in review.** That is the behaviour
the rules ask for and it is worth recording as such: each one below cost a line in a report instead
of a defect in a later card.

### 1. The admissions queue's `missing` column cannot see steps 3 to 8

6.5.11 step 9 blocks approval when "any required item across steps 1 to 8 is missing". The queue's
`missing` column can only check what sections A and I store today:

```
assessmentRequired && no assessmentResultRemarks  →  "Assessment result (Section A)"
!declarationSigned                                →  "Declaration (Section I)"
```

Steps 3 to 8 — contacts, health, barred persons, authorised-pickup persons, documents — have **no
entity in this repo**, so a gap there can never appear in `missing`. The column is therefore honest
about what it checks and silent about what it cannot, which is the correct failure mode, but a
reader who assumes an empty `missing` means "ready to approve" will be wrong until those entities
exist. Section B's own conditional requirements are equally unchecked, and were equally unchecked by
TASK-0050 before this card.

*Trigger: each of the step 3-to-8 entity cards as it lands, and TASK-0051, whose approval path must
NOT present this list as a complete pre-approval gate. Owner: `backend-dev`.*

### 2. `headOfSchoolName` has no settings-derived default

6.5.9's field table says **"Defaults from settings."** The implemented field stays `null` until a
caller supplies it. The agent's stated reason — no acceptance criterion named it, and wiring it
would pull a new dependency into the card for a cosmetic default — is a fair scope call, but the
spec sentence is unambiguous and this is a deviation from it rather than a silence in it.

**This is the one of the three that is a genuine spec deviation rather than a consequence of
unbuilt dependencies**, which is why it is recorded separately rather than folded into gap 1.

*Trigger: TASK-0051, which writes section J at approval and is the natural place to read the
setting. Owner: `backend-dev`.*

### 3. `admission` is `null` on `GET /pupils/{id}` and `PATCH /pupils/{id}`

Only `CreatePupilHandler`'s own response populates `PupilDto.Admission`. Every other pupil read path
returns it `null`, because populating it means joining `admission_records` into those queries.

6.5.15's detail view explicitly lists "**Admission record**: sections A, I and J, including who
approved and when" as one of its blocks, so the detail screen cannot be built against the current
shape. The contract does not lie about this — the field is optional and its OpenAPI description
names exactly which path populates it — but the field existing while always being null on the one
read path that needs it is a trap for whoever writes that screen.

Note this is the same pattern `PupilDto.MatchedField` already uses (populated only by search), so
the shape is consistent with the repo rather than novel.

*Trigger: the pupil detail-view card, or TASK-0051 if it finds itself needing the record on a read
path. Owner: `backend-dev`.*
