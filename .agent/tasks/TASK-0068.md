## Goal

A pupil whose surname contains an apostrophe stops vanishing from the pupil register when the
administrator pages past them, and paging into the leavers block stops loading every leaver in the
school's history into memory.

## The defect, in one example

`Oakes` and `O'Brien` in the same arm. The register orders one group of rows in SQL
(`ORDER BY lower(surname)`, database collation) and the other in .NET (`StringComparer.Ordinal-
IgnoreCase`). A locale-aware collation ignores the apostrophe and sorts `Oakes` first; ordinal does
not and sorts `O'Brien` first. Page N ends at `Oakes`; page N+1 asks the same bucket for surnames
ordinally after `oakes`; `o'brien` is ordinally BEFORE it. O'Brien appears on no page at all.

None expected. See the header.

## Acceptance criteria

- [ ] **Both halves of the register read compare surnames identically**, whichever way part 1 is
      ruled. A test with a punctuated surname (`O'Brien` alongside `Oakes`, same arm) pages across
      the seam and asserts every pupil appears exactly once, on exactly one page.
- [ ] The same test exists for the trailing unenrolled block, not only for a class bucket — the
      sentinel bucket is a different code path.
- [ ] **The sentinel bucket's fetch is bounded.** Paging into the leavers block must not materialise
      every unenrolled pupil in the school; prove it with a test that seeds more leavers than one
      page and asserts the query does not load them all, or restructure so the question cannot arise.
- [ ] Existing ordering behaviour for ASCII-only surnames is unchanged — the TASK-0061 tests still
      pass untouched.
- [ ] The admissions queue stays byte-for-byte unaffected, exactly as TASK-0061 required.
- [ ] `contracts/openapi.json` byte-unchanged, UNLESS the orchestrator has approved a description
      delta first.

## Notes for the implementing agent

**Part 1 needs a human ruling and this card must NOT be dispatched until it has one.** There are two
defensible fixes and they differ in blast radius, so this is not the agent's call:

- **(a) Pin an explicit collation on `pupil.surname`** (e.g. `C` or a deterministic ICU collation) so
  SQL and .NET agree by construction. Correct and cheap, but it is a migration on an existing column,
  it changes ordering for EVERY query that touches surname, and it interacts with **Open question 5**,
  the still-undecided production database target.
- **(b) Do the same-bucket comparison in SQL too**, so .NET never orders anything. Narrower blast
  radius, but it runs straight into the Npgsql limitation TASK-0061 documented — the reason the split
  exists at all — so it may need a raw-SQL fragment or a different query shape.

Do not pick one yourself, and do not implement both.
