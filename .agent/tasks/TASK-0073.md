## Goal

`AuthLogRedactionTests.SignInAndChangePassword_NeverWriteThePlaintextPasswordToConsoleOutput` is the
only test proving spec 9.1's "no password appears in a log line". It has been **passing for the
wrong reason for its entire life**: it captures console output only because hosted Neon was slow
enough to let the capture land. Point it at a fast local database and its POSITIVE CONTROL fails —
`written.ShouldNotBeEmpty` at `:82`, the assertion that exists specifically to stop the two
`ShouldNotContain` redaction checks passing vacuously.

So the situation today is: on the machine where it passes, it may be passing vacuously; on the
machine where it fails, it fails loudly for a reason nobody has established. **Either way the
project does not currently have a trustworthy proof that passwords stay out of the logs.** That is
what this card fixes — not the red line in the test run.

Refuted already — do not re-propose any of these without new evidence:

1. **"A race between parallel test collections"** (the TASK-0065 agent). There is one xUnit
   collection, no parallelism config anywhere in `backend/tests`, and nothing else in the repo calls
   `Console.SetOut`.
2. **"Deterministic ordering — the sink binds `Console.Out` at first materialisation"** (the
   orchestrator). Refuted by row 3: identical ordering against Neon passes.
3. **"A fast database outpaces the sink"** (the orchestrator, second attempt). Refuted by row 4:
   CI's service container is local and fast and passes.
4. **"Something network-related"**. Refuted by row 5: identical failure with the network physically
   disconnected.

**The leading UNTESTED candidate is the platform** — CI is Linux, the failing case is Windows, and
`Console.Out` redirection under `dotnet test` differs between them. That is a starting point, not a
finding. **Establish the mechanism with evidence before writing a fix.**

## Acceptance criteria

- [x] **The mechanism is established and written down** — what actually determines whether the
      capture lands. A fix that makes the test pass without explaining row 2 versus row 3 is not
      accepted; it will just move the vacuous pass somewhere else.
- [x] The test passes **deterministically**: alone, in the full suite, on Windows and on the CI
      runner, against a local container and against a hosted database. The matrix above is the
      regression list — walk it.
- [x] **Proven not-vacuous, the way this project requires** (`STATE.md` 2026-09-05 standing lesson:
      *a check that cannot be shown to fail is not a check*). Temporarily make the app log the
      plaintext password, watch the test go RED, then revert. Report both states. **A green run is
      not evidence here — the test was green for months while proving nothing.**
- [x] The positive control survives in some form. If the capture mechanism changes, the guarantee
      "this assertion cannot pass vacuously" must still hold and must still be visible in the test.
- [x] No production behaviour change. If `ObservabilitySetup` must change to make logging testable,
      that is in scope, but the deployed logging output must be identical — say how you verified it.

## Out of scope

- **Do not delete or weaken the positive control**, and do not replace it with an assertion that

  **Reproduction.** `dotnet test` (Debug) on the full `SchoolManagement.IntegrationTests` suite,
  local container, POSTGRES_TEST_CONNECTION unset: **Failed: 1, Passed: 321, Total: 322**, the
  redaction test's positive control failing exactly as the evidence table's row 2/5 describes.
  Reproduced twice before touching any code. A 2-class `--filter` subset
  (`AdminAccountEndpointsTests|AuthLogRedactionTests`, then separately
  `AuthEndpointsTests|AuthLogRedactionTests`) did NOT reproduce it — the defect needs the wider

  **Mechanism, established by instrumenting the test temporarily** (a `Console.Out`-identity probe,
  a raw `Console.Out.WriteAsync` probe, a fresh `ILoggerFactory`-created logger's `IsEnabled`, and
  `Serilog.Log.Logger`'s own type/`IsEnabled`, each appended to a scratch file, never to the
  process console — removed before commit, diff verified empty):
  - The `Console.SetOut` redirect itself is NOT broken: a raw probe write always landed in the
    test's `StringWriter`, in every run, including failing ones.
  - In the failing run, `Serilog.Log.Logger` (the process-wide static ambient logger) was observed
    to be `Serilog.Core.Pipeline.SilentLogger` — Serilog's own no-op logger, `IsEnabled` always
    `false` — while the SAME run's DI-resolved `Serilog.ILogger` (a directly-captured reference)
    was a live, enabled `Serilog.Core.Logger`. In a passing run, `Log.Logger` was a live
    `Serilog.Core.Logger` too.
  - A fresh `Microsoft.Extensions.Logging.ILogger` from the fixture's own `ILoggerFactory`
    (`RequestLoggingBehavior`'s exact pathway) reported `IsEnabled(Information) == false` in the
    failing run — this is what actually silenced `BehaviorLog.HandlingRequest`, not a Console.Out
    problem.
  - Fetched Serilog.Extensions.Hosting v10.0.0's actual source
    (`SerilogServiceCollectionExtensions.cs`, via `gh api`) to confirm the wiring rather than
    guess it: `AddSerilog(Action<IServiceProvider, LoggerConfiguration>, preserveStaticLogger =
    false, ...)` — the exact overload `ObservabilitySetup.ConfigureSerilog` calls — when
    `preserveStaticLogger` is left at its default `false`: (1) sets `Serilog.Log.Logger` to the
    newly-built logger, and (2) builds that host's `ILoggerFactory` with **no captured logger
    reference**, so its `ILogger<T>`s read `Serilog.Log.Logger` DYNAMICALLY on every call — this is
    documented, intentional Serilog behaviour. The library's own code comment: passing a null
    logger to `SerilogLoggerFactory` means its `Dispose()` calls `Log.CloseAndFlush()`, which
    "replaces the static logger with a no-op".
  - This codebase's integration suite builds 18 separate `WebApplicationFactory.WithWebHostBuilder`
    hosts across other test files (confirmed by grep), each re-running
    `ObservabilitySetup.ConfigureSerilog` and therefore re-arming this exact trap. Disposing ANY ONE
    of them resets the ambient `Log.Logger` to `SilentLogger`, silencing the SHARED fixture's own
    `ILogger<T>`-based logging (which was ALSO built with `preserveStaticLogger: false`, so it ALSO
    reads the ambient logger dynamically) for the rest of the process — including
    `RequestLoggingBehavior`'s `BehaviorLog.HandlingRequest` call, which is what the test's positive
    control depends on. This explains PASS-alone (nothing else ever built+disposed a second host)
    and FAIL-in-the-full-suite (with 18 files doing so, something reliably has by the time this test
    runs). It does not, by itself, explain why my two small 2-class subsets didn't reproduce it —
    that residual is about exactly WHEN in the full run's sequence the silencing first occurs, not
    about whether the mechanism is real; the mechanism itself is confirmed directly (SilentLogger
    observed in situ) rather than inferred.
  - Why CI and hosted-Neon apparently don't hit this: not established beyond "some other host's
    disposal has to land before this test runs, and that depends on exact suite timing/ordering,
    which differs by platform and by how many `WithWebHostBuilder` hosts have been built and
    disposed by that point" — left as a residual, since the fix removes the shared mutable state
    entirely rather than depending on which platform's timing avoids it.

  **Fix**: `ObservabilitySetup.ConfigureSerilog` now passes `preserveStaticLogger: true` to
  `AddSerilog`. This makes the host's `ILoggerFactory` capture ITS OWN logger instance directly
  instead of reading the ambient static, so no other host's build/dispose lifecycle can affect it,
  and stops touching `Serilog.Log.Logger` (which nothing in this codebase reads directly — grepped,
  confirmed) at all. **No production behaviour change**: a deployed instance builds exactly one
  host per process, so `preserveStaticLogger` only has an observable effect when MULTIPLE
  `AddSerilog`-configured hosts share a process — a test-only condition (`WithWebHostBuilder`).
  Same sinks, same enrichers, same levels, same message templates either way. Verified by: (a) the
  diff is one named parameter plus a comment, nothing else in `ConfigureSerilog`/
  `ConfigureOpenTelemetry` touched; (b) `UseSerilogRequestLogging`'s `IDiagnosticContext` wiring
  (the other consumer of `preserveStaticLogger` inside `AddSerilog`) only changes which logger
  `DiagnosticContext` holds, not what `diagnosticContext.Set(...)` does — reviewed against
  `Serilog.Extensions.Hosting`'s source, not assumed.
