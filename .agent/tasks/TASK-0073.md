## Goal

`AuthLogRedactionTests.SignInAndChangePassword_NeverWriteThePlaintextPasswordToConsoleOutput` is the
only test proving spec 9.1's "no password appears in a log line". It has been **passing for the
wrong reason for its entire life**: it captures console output only because hosted Neon was slow
enough to let the capture land. Point it at a fast local database and its POSITIVE CONTROL fails —
`written.ShouldNotBeEmpty` at `:82`, the assertion that exists specifically to stop the two
`ShouldNotContain` redaction checks passing vacuously.

So the situation today is: on the machine where it passes, it may be passing vacuously; on the
machine where it fails, it fails loudly for a reason nobody has established. **Either way the
project does not currently have a trustworthy proof that passwords stay out of the logs.** That is
what this card fixes — not the red line in the test run.

## The evidence — four explanations have already been wrong. Start here, not from a hypothesis.

| Environment | Database | Earlier class ran first? | Result |
|---|---|---|---|
| local Windows | WSL container | no (test alone) | PASS |
| local Windows | WSL container | **yes** | **FAIL** |
| local Windows | hosted Neon | yes | PASS |
| CI, ubuntu runner | service container | yes (full suite) | PASS |
| local Windows, **network disconnected** | WSL container | yes (full suite) | **FAIL** |

Refuted already — do not re-propose any of these without new evidence:

1. **"A race between parallel test collections"** (the TASK-0065 agent). There is one xUnit
   collection, no parallelism config anywhere in `backend/tests`, and nothing else in the repo calls
   `Console.SetOut`.
2. **"Deterministic ordering — the sink binds `Console.Out` at first materialisation"** (the
   orchestrator). Refuted by row 3: identical ordering against Neon passes.
3. **"A fast database outpaces the sink"** (the orchestrator, second attempt). Refuted by row 4:
   CI's service container is local and fast and passes.
4. **"Something network-related"**. Refuted by row 5: identical failure with the network physically
   disconnected.

**The leading UNTESTED candidate is the platform** — CI is Linux, the failing case is Windows, and
`Console.Out` redirection under `dotnet test` differs between them. That is a starting point, not a
finding. **Establish the mechanism with evidence before writing a fix.**

## Acceptance criteria

- [ ] **The mechanism is established and written down** — what actually determines whether the
      capture lands. A fix that makes the test pass without explaining row 2 versus row 3 is not
      accepted; it will just move the vacuous pass somewhere else.
- [ ] The test passes **deterministically**: alone, in the full suite, on Windows and on the CI
      runner, against a local container and against a hosted database. The matrix above is the
      regression list — walk it.
- [ ] **Proven not-vacuous, the way this project requires** (`STATE.md` 2026-09-05 standing lesson:
      *a check that cannot be shown to fail is not a check*). Temporarily make the app log the
      plaintext password, watch the test go RED, then revert. Report both states. **A green run is
      not evidence here — the test was green for months while proving nothing.**
- [ ] The positive control survives in some form. If the capture mechanism changes, the guarantee
      "this assertion cannot pass vacuously" must still hold and must still be visible in the test.
- [ ] No production behaviour change. If `ObservabilitySetup` must change to make logging testable,
      that is in scope, but the deployed logging output must be identical — say how you verified it.

## Out of scope

- **Do not "fix" it by reordering or renaming test classes.** That hides it behind whatever order
  xUnit happens to pick and re-arms the same trap for the next person.
- **Do not delete or weaken the positive control**, and do not replace it with an assertion that
  cannot distinguish "nothing was logged" from "the password was redacted". That control is the
  entire reason this defect was visible at all.
- Do not change what the application logs, or its redaction enrichers' behaviour.
- Do not run the full gate (`rules/gates.md` §1).

## Notes for the implementing agent

`IdempotencyTestHost.cs` in this same suite already builds a second, purpose-built host against the
shared migrated database. If the fix is "this test needs its own host, built inside the redirect",
that pattern is the precedent and it is already sanctioned.

`ObservabilitySetup.cs:63` is `.WriteTo.Console()` plugged into the DI-built logger via
`AddSerilog((services, configuration) => ...)`, with `ReadFrom.Configuration` ahead of it — so the
test's `appsettings` can influence level and sink shape. Worth understanding before assuming the
sink is the problem.

**This test is the only thing standing between a password-logging regression and production.** Treat
a fix that merely turns the line green as a failure of the card.
