# TASK-0038 — Sections, class levels and the progression chain

arms are now TASK-0039, which is what TASK-0030 and the two TASK-0035 drifts actually wait on.

> **Scope trap, read this first.** A level is a year group that persists across sessions and sits
> in an ordered chain. An arm is one room for one session. Spec 6.4.1 separates them deliberately.
> **This card is levels only.** Every arm concern — creation, capacity, bulk, form teachers, the
> `open`-term arm precondition, the session arm counts — is TASK-0039. Do not reach for it.

## Goal

An administrator can manage the school's year groups and the order they run in, and the system
guarantees that order is coherent: one entry level, one graduating level, no cycles, everything
reachable. Promotion (TASK-0036) later walks this chain, and arms (TASK-0039) hang off it, so the
chain being self-consistent at rest is the whole point of the card.

## Contract delta

All additive. **Every privilege constant already exists** in `Domain/Security/Privileges.cs`
(`Level.View/Create/Update/Deactivate/Delete`) — do not invent codes or touch the 93-row register.

| Endpoint | Privilege | Notes |
|---|---|---|
| `GET /api/v1/sections` | `level.view` | The admin-editable section list. Not paged — a two-row seeded list a school extends rarely. |
| `POST /api/v1/sections` | `level.create` | `Idempotency-Key` REQUIRED. |
| `PATCH /api/v1/sections/{id}` | `level.update` | Name only. |
| `GET /api/v1/levels` | `level.view` | Active by default, `?status=all` returns inactive too (spec 6.4.9). Ordered by `progressionOrder`. Carries `isEntryLevel` and `isGraduatingLevel` as **derived** booleans. Cursor-paginated per §9.5 like every other list, even though the list is short. |
| `POST /api/v1/levels` | `level.create` | Body may carry `insertAfterLevelId`; when present the server rewires the chain and reorders **in one transaction** (spec 6.4.2 worked case). `Idempotency-Key` REQUIRED. |
| `GET /api/v1/levels/{id}` | `level.view` | Detail. **No arm counts** — that is TASK-0039. |
| `PATCH /api/v1/levels/{id}` | `level.update`, plus `level.deactivate` when the body changes `status` | Name, section, next level, order, status. Reruns all eight rules. |
| `POST /api/v1/levels/reorder` | `level.update` | Whole ordered array of level ids. Atomic. Rewrites `progressionOrder` **and** infers `nextLevelId` from adjacency, per 6.4.2. |
| `DELETE /api/v1/levels/{id}` | `level.delete` | Permitted only where nothing has ever referenced the level. `409` naming the references otherwise. |

`section` and `status` cross the wire as strings; the client tolerates unknown members (§8).
`isEntryLevel`/`isGraduatingLevel` are computed at read time and **never stored** — storing them
is the same class of defect as storing `display_name`, which 6.4.3 forbids for the same reason.

## Acceptance criteria

- [x] Nine levels seeded (Nursery 1-3, Primary 1-6) chained in that order with Primary 6
      graduating, and two sections (Nursery, Primary). Seeded by migration, idempotent on re-run.
- [x] **Nothing in code assumes those nine, their names, or that the chain stays inside a
      section** (spec 6.4.2). A test adds a tenth level and asserts the chain still validates.
- [x] All eight chain rules enforced, each with the spec's own rejection message. **PARTIAL on
      "each with its own failing test", declared not silent:** rules 4-plural, 5 and 6 are
      mathematically implied by rule 3 and cannot be isolated as standalone `Validate` failures
      (counting argument in `ASSUMPTIONS.md` §2.23). Three tests construct the natural attempt at
      each and show rule 3 firing instead. Consequence — those three spec messages are unreachable
      — is `STATE.md` open question 13. Validation runs **over active levels only, as one set**, on every save
      touching name, order, next level or status. Rules 3b and 4b are separate cases from 3 and 4.
- [x] A save that breaks any rule is **rejected whole** — assert the transaction rolled back, not
      merely that a 422 came back.
- [x] The 6.4.2 worked case passes end to end: inserting Reception after Nursery 3 creates it with
      order 4, points Nursery 3 at it and it at Primary 1, and shifts Primary 1-6 up by one — in
      one transaction, with the eight rules rerun before commit.
- [x] Deactivating Nursery 1-3 in turn leaves Primary 1 as the entry level with **no** requirement
      to clear Nursery 3's pointer, and reactivation restores the original chain (spec 6.4.2).
- [x] Deactivating a mid-chain level is rejected with the spec's unreachability message.
- [x] `DELETE` succeeds only where nothing has ever referenced the level. With no arm, enrolment,
      mapping or result table existing yet for most of those references, assert what CAN be
      asserted honestly and record the rest in `ASSUMPTIONS.md` — **do not ship an always-true
      probe** (see Notes).
- [x] Renaming a level does not rewrite anything already published — assert against the
      configuration-snapshot mechanism from 6.2.9, not by re-reading the level.
- [x] Uniqueness of `name` (case-insensitive, trimmed) and of `progressionOrder` across active
      levels enforced by a **database index**, not only by application validation.
- [x] `openapi.json` regenerated via `scripts/generate-openapi.ps1 -Promote`; `CONTRACT.lock`
      updated; all ten §9 gates green with the `SUMMARY` block pasted.

## Notes for the implementing agent

Read `product-specification/06-module-class-levels-arms.md` §6.4.1, 6.4.2, 6.4.7, 6.4.8 and 6.4.9
in full first — §6.4.3 to §6.4.6 are arms and belong to TASK-0039.

Follow the module shape TASK-0035 established, which is the closest and most recent precedent:
`Domain/Sessions/`, `Application/Sessions/`, `Api/Endpoints/SessionEndpoints.cs`,
`Infrastructure/Persistence/Configurations/`, `.../Repositories/`. Put this card's work in
`Domain/Classes/` — **not** `Domain/Levels/`, because TASK-0039's arms join it there.

`AcademicSession.Create` and `TermTransitionGuard` are the two patterns worth copying: invariants
enforced in the domain type rather than the handler, and a guard type owning a rule set that has
its own unit tests independent of any database. **The eight chain rules belong in a
`ProgressionChainGuard` of that shape** — a pure function over a set of levels, unit-testable
without Postgres, per TASK-0009's standing lesson that database-free checks must stay
database-free.

**On the delete precondition, and this is the one that matters.** "Nothing has ever referenced
it" spans arms, enrolments, subject mappings and results — three of which do not exist yet. The
project already has one always-true bypass it regrets (`SuperAdminFlagEffectivePrivilegeProvider`)
and TASK-0035 explicitly refused to add a second. Do the same here: check the references that
exist, mark the seam `DEFERRED` in a comment naming this card and the tables still missing, and
append the deviation to `backend/docs/ASSUMPTIONS.md` §2. Report it so it lands in
`STATE.md ## Known drift` with TASK-0039 and the Phase 2/3 cards as its triggers.

**One ruling you do not need to ask about:** spec 6.4.9 needs section endpoints and the fixed
93-row register has no `section.*` code. Gate them under `level.view/create/update` as tabled
above. A section is a property of a level, and inventing register rows is the larger deviation.
Flag it in your report; do not add privileges.
