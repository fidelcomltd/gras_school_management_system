# TASK-0051 — Registration number issue and the admission-approval transition

Owner: backend-dev
Depends on: **TASK-0005c** (settings: pattern, `serial_reset`, serial width) — **not yet written**,
and TASK-0050 (the pupil entity), and an `enrolment` entity that does not exist yet.
Contract impact: additive — `POST /admissions/{id}/approve`, `POST /admissions/{id}/decline`,
`POST /pupils/{id}/registration-number`.
Status: **blocked** (stub — write in full just before dispatch)

## Why this is blocked and not merely queued

6.5.10's number is composed from the **saved settings** — abbreviation, separator, serial width and
`serial_reset` — none of which exist until TASK-0005c lands. A card that hardcoded
`GRAS/2026/0041`'s shape would be inventing configuration the school owns.

Carried here so it is not rediscovered:

- **The counter mechanism is prescribed, not a choice.** 6.5.10: a `registration_counter` table,
  one row per counter key, and `INSERT ... ON CONFLICT (counter_key) DO UPDATE SET last_serial =
  registration_counter.last_serial + 1 RETURNING last_serial`. That takes a row lock and serialises
  concurrent approvals. **The counter is never derived from the pupil table** — "counting existing
  pupils and adding one is the mechanism that produces duplicates", explicitly including the import
  path. A `MAX(serial) + 1` anywhere in this card is a review blocker.
- **Counter key depends on the saved `serial_reset`**: the admission year as a string under
  `per_year`, the fixed string `ALL` under `continuous`. This is TASK-0005c's delta amendment 1 —
  a counter keyed on year alone cannot express `continuous`, and would accept the setting while
  changing nothing.
- **The year is the admission year** from `admission_record.date_admitted`, **not** the current
  year. A pupil admitted September 2026 whose approval is entered January 2027 still gets 2026.
- **The abbreviation is frozen into the stored string at issue.** Changing it later never rewrites
  an issued number.
- `Idempotency-Key` **required** on approve (6.5.17) — "so a retry cannot issue two numbers". This
  is the single most important idempotency case in the product.
- The unique index on `pupil.registration_number` is the backstop; on violation, retry the whole
  transaction up to **three** times, then fail with verbatim `Could not issue a registration
  number. Try again.`
- **Correction** (`pupil.regnumber.correct`, Super Admin only, reason ≥ 10 chars): the administrator
  types the new number **in full** — the system does not generate it. Old number goes to
  `pupil_reg_number_history` and stays permanently as a **portal lookup alias**, with the verbatim
  redirect notice `This pupil's registration number is now GRAS/2026/0041. Use that number in
  future.` Published result snapshots are **not** rewritten.
- Approval also opens the first enrolment and sets `status = active` (6.5.14) — so this card needs
  `enrolment`, which is unbuilt. **Decide at write-up time whether enrolment is a third dependency
  or its own preceding card.**
- Decline sets `withdrawn` **without issuing a number**, so no serial is consumed.
- **`abbreviation.issuedCount`** — TASK-0005c ships it nullable, `null` meaning "no register to
  count". This card is the one that makes a real count possible; wiring it is a live drift trigger
  in `## Known drift`, and the settings-screen frontend card must stop suppressing the count
  sentence once it is non-null.
