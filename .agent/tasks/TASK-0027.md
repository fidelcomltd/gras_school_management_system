# TASK-0027 — Admin account management

Owner: backend-dev
Depends on: TASK-0019 (substrate must close first)
Contract impact: additive — seven endpoints plus the `Idempotency-Key` header declaration
Status: **blocked — awaiting human sign-off (§5)**

## Why it is blocked

Two of the seven endpoints are session/credential operations: `POST /admins/{id}/password-reset`
(mints a new temporary password, revokes every session) and `DELETE /admins/{id}/sessions`.
Suspension and deactivation also revoke sessions. CLAUDE.md §5 — "session/auth changes are always
treated as a contract change requiring human sign-off." The mechanism is unchanged from TASK-0003;
what is new is who may operate it on whose behalf. That is the question for the human.

## Goal

A Super Admin creates, edits, suspends, reactivates, deactivates, force-resets and signs out
administrator accounts, with the invariants spec 4.1 and 6.1.7 rule 4 require.

## Acceptance criteria

- [ ] All seven endpoints, cursor-paginated per §9.5 (never offset — the existing
      `PagedResultOfSampleRecordDto` is offset-based and must NOT be reused), deactivating rather
      than deleting per §9.4.
- [ ] Every endpoint privilege-checked as server middleware (§9.2), per the privilege column in
      spec 6.1.2. `Privileges.Admin.*` is already registered — use it, do not invent names.
- [ ] **`Idempotency-Key` declared** per the approved delta: REQUIRED on `POST /admins`, accepted
      on `PATCH`, `status`, `password-reset`; and the `Idempotency-Replay` response header is
      DECLARED IN THE DOCUMENT BY CONSTRUCTION — a marker read by an operation transformer, the way
      `CsrfHeaderOperationTransformer` does it. Hand-annotation is not acceptable; prose is not
      declaration. TASK-0003 was reopened over precisely this.
- [ ] A test proves a duplicate `POST /admins` with the same key creates exactly one account.
- [ ] **`temporaryPassword` is redacted from the stored idempotency response** (TASK-0019's hook),
      with a test reading the stored row back. Spec 6.1.9/6.1.14: displayed once, never again.
- [ ] **At least one active Super Admin exists at all times** (spec 4.1), enforced transactionally
      with a row lock — not a pre-flight read — with a test for the attempted-removal-of-the-last-one
      case and one for two concurrent attempts.
- [ ] **6.1.7 rule 4**: `is_super_admin` settable only by an account that already holds it, with a
      test, and **an audit event on the rejected attempt** (6.1.7 preamble requires this).
- [ ] **Self-edit carve-out (6.1.2)**: a caller without `admin.update` may change **only their own
      `staffName` and `phone`** — NOT their own email, which stays `admin.update`-gated. Test both.
- [ ] **Session revocation on state change (6.1.10)**: suspension revokes existing sessions
      immediately; deactivation revokes sessions; `password-reset` revokes every session. Tests each.
- [ ] Reactivation `deactivated -> active` requires `admin.deactivate` **held by a Super Admin**
      (6.1.10) and does NOT restore assignments.
- [ ] Session tokens rotate on privilege change (spec 9.1) — TASK-0003 built rotation, the
      `is_super_admin` flag change is where a privilege change first actually happens. Prove it fires.
- [ ] **Fix `UseRateLimiter()` running before `UseAuthentication()`** (`Program.cs:298` vs `:300`),
      then prove the per-user partition is live — a 429 test that would still pass under IP
      partitioning does not satisfy this criterion. This is the drift trigger this card inherits.
- [ ] Email uniqueness across **active and suspended** accounts, case-insensitive (6.1.3); a
      deactivated account's email is reusable.
- [ ] `./backend/scripts/ci.ps1` green with the integration suite RUNNING (`Skipped: 0`).

## Out of scope

- Consequently omitted from the DTOs, to be added additively by TASK-0028: `rolesHeld` /
  `scopeSummary` on the list item; assignments, effective privileges and last-ten-audit-events on
  the detail view (6.1.8); the role / scope-arm / session list filters.
- **Deactivation's "all active assignments are revoked" half** (6.1.10) — nothing to revoke until
  TASK-0028 exists. That card wires it; this card must leave the seam obvious, not silently correct.
- Admin account screens.
- The audit log READ surface (`GET /audit`, `/audit/export`). Audit event WRITES are in scope and
  transactional (6.1.12) — the read surface is the Phase 1 roadmap row.
