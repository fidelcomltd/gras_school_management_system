# TASK-0053 — Neutralise CSV formula injection in the audit export

Owner: backend-dev
Depends on: TASK-0049 — the export exists there. Nothing else blocks this.
Contract impact: **none.** The response is still `text/csv` with the same thirteen columns; only
field *encoding* changes. No path, schema or status code moves.
Status: queued
Reads: `.agent/spec/backend.md`, `.agent/rules/wire.md`, `.agent/rules/gates.md`; `jq` the
       `/api/v1/audit-events/export` path only; `grep TASK-0049` in `.agent/decisions/2026-Q3.md`

## Goal

An `audit.export` holder can open the exported CSV in Excel, LibreOffice or Sheets without any
cell being interpreted as a formula. Today a field beginning `=`, `+`, `-` or `@` is executed by
the spreadsheet on open, and one of those fields is set by whoever made the request being logged.

## Why this is real, not theoretical

Found by the orchestrator during TASK-0049 diff review; not raised by the implementing agent.

`AuditEventCsvWriter.Escape` in `backend/src/SchoolManagement.Api/Endpoints/AuditEventEndpoints.cs`
implements RFC 4180 correctly — a field containing `,`, `"`, `\r` or `\n` is quoted and embedded
quotes are doubled. RFC 4180 is the wrong threat model on its own: **quoting does not stop formula
interpretation.** A cell whose value is `=1+1` is still a formula when written as `"=1+1"`.

The reachable path:

1. `user_agent` is captured verbatim from the request header (`AuditEventFactory` line 65, via
   `AuditFieldTruncation.TruncateUserAgent(currentUser.UserAgent)`) and is set by whoever sent the
   request — including an unauthenticated attacker, since failed sign-ins are audited.
2. That row lands in `audit_event` and is returned by `GET /api/v1/audit-events/export`.
3. An `audit.export` holder — Auditor or Super Admin, by seeding — opens the file in Excel.
4. The cell executes. `=HYPERLINK` or `=WEBSERVICE` exfiltrates the surrounding rows, which are
   the audit trail, to an attacker-controlled URL. Excel prompts for some functions, but the
   prompt is a "this file contains links, update?" dialogue that office staff click through.

So the attacker needs no account, and the victim is by definition the most privileged reader in
the product. `reason` and `action` are lower-risk variants of the same class.

**This is not a TASK-0049 defect.** That card did not ask for it, its CSV is correct per its own
acceptance criteria, and the columns are exactly the thirteen 6.1.12 defines. This is a separate,
narrower piece of work.

## Acceptance criteria

- [ ] A field whose first character is `=`, `+`, `-`, `@`, TAB (`0x09`) or CR (`0x0D`) is
      neutralised before being written. Prefix with a single apostrophe (`'`) — the conventional
      fix, understood by Excel, LibreOffice and Sheets — **after** the RFC 4180 quoting decision,
      not instead of it. The two mechanisms are independent and both must apply.
- [ ] Neutralisation is applied to **every** field, not just `userAgent`. `reason`, `action`,
      `actorLabel`, `entityType`, `beforeJson` and `afterJson` are all free-ish text; enumerating
      "the dangerous ones" is how the next one gets missed. Cheap enough to apply uniformly.
- [ ] `-` is handled carefully: a legitimate negative number is not currently emitted by any of
      the thirteen columns, so blanket-prefixing `-` is safe **today**. State that assumption in a
      comment so a future column carrying a signed number is not silently mangled.
- [ ] A unit test per dangerous leading character, asserting the written cell round-trips as
      literal text and not as a formula.
- [ ] An integration test that seeds an audit row with `user_agent` set to `=HYPERLINK("http://evil","x")`,
      exports, and asserts the CSV cell is neutralised. This is the actual attack, end to end.
- [ ] A test asserting the RFC 4180 behaviour is **unchanged** — a field containing a comma is
      still quoted, embedded quotes still doubled. This card must not regress TASK-0049's escaping.
- [ ] The stream stays lazy. Neutralisation is per-field and allocation-light; do not materialise
      the filtered set to pre-scan it.
- [ ] `openapi.json` regenerated and **unchanged** — this is an encoding fix, so the promoted
      document's hash must not move. If it moves, something widened that should not have.

## Out of scope

- **Changing which columns the CSV carries.** The thirteen are 6.1.12's, and TASK-0049's PII
  criterion forbids widening. Do not add or remove one.
- **The stored value.** `audit_event.user_agent` keeps the verbatim (truncated) header — the log
  must record what was actually sent. This is an export-encoding fix only; sanitising at write time
  would falsify the trail.
- **Any other export in the product.** There is currently only this one. When report exports arrive
  they inherit the same problem — note it in that card rather than pre-building a shared helper
  here for a single caller.
- The `SameSite=Lax` CSRF question on the export route (TASK-0049 known drift) — separate concern,
  belongs with the audit-log screen card.

## Notes for the implementing agent

The whole change is `AuditEventCsvWriter`, and it should be well under 60 production lines. If it
is growing past that, you have widened the scope.

Order of operations is the one thing to get right: **neutralise the value, then apply RFC 4180
quoting to the result.** Reversed, a neutralised field containing a comma stops being quoted
correctly and the row gains a column.

Do not "improve" the escaper beyond this. TASK-0049's RFC 4180 logic is correct and tested; this
card adds one orthogonal step in front of it.

**Gates.** `.agent/rules/gates.md` section 1: the **orchestrator** runs `ci.ps1`, once,
backgrounded. You verify with `dotnet test --filter` over what you touched and report the counts.
You verify with `dotnet test --filter` over what you touched and stop. Do not run the full gate.
