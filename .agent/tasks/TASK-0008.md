# TASK-0008 — Give the integration-test connection string a durable local home

Owner: backend-dev
Depends on: —
Contract impact: none
Status: done

## Goal

`POSTGRES_TEST_CONNECTION` is read straight from the process environment by
[DatabaseAvailability.cs](../../backend/tests/SchoolManagement.IntegrationTests/Infrastructure/DatabaseAvailability.cs),
deliberately, so the harness behaves identically locally and in CI. The consequence is that a
developer has no sanctioned place to keep it: it must be re-typed or re-pasted every session, and
the failure mode when they forget is silent — the integration tests **skip** and the suite still
reports success. That is the exact failure `.github/workflows/backend-ci.yml` guards against in
CI, and locally there is no guard at all.

Give it a home that is outside version control, one command to use, and impossible to commit.

None.

## Acceptance criteria

- [x] A gitignored local script — suggested `backend/scripts/local-env.ps1` — sets
      `POSTGRES_TEST_CONNECTION` (and any future local-only variable) and then invokes the
      requested gate, so the whole flow is one command.
- [x] A committed `backend/scripts/local-env.template.ps1` documents every variable, its shape and
      an example value, with **no real credential**. Follows the precedent already set by
      `appsettings.Development.template.json`.
- [x] `backend/.gitignore` excludes the real script and **not** the template. Verify with
      `git check-ignore -v` on both paths and paste the output — a `.gitignore` rule that
      accidentally also ignores the template silently removes the documentation.
- [x] `gitleaks` still passes, and the template does not trip it. If the example value looks
      credential-shaped enough to trigger a rule, make the example obviously fake rather than
      adding a `.gitleaks.toml` allowlist entry — an allowlist entry is a permanent hole, a fake
      example is not.
- [x] The script must **never echo the connection string**, on success or on failure. Check
      `ci.ps1` still only reports whether the variable is set, never its value (spec 9.1: no
      credential in a log line).
- [x] `backend/README.md`'s "Configuration and secrets" section explains the new script, why this
      one variable is an environment variable rather than user-secrets (it bypasses
      `IConfiguration` entirely so user-secrets cannot reach it), and that the file is local-only.
- [x] A developer with no prior setup can go from a fresh clone to running integration tests by
      following only the README.
- [x] **Install `gitleaks` locally and document it as required setup.** `ci.ps1` currently reports
      `PASS: Secret scan` with a warning that gitleaks is not installed — so locally there is no
      secret scanning at all, and the gate's green is meaningless. CI installs it, so pushes are
      covered, but this card is specifically about creating a local file whose purpose is holding a
      live credential; shipping that without local scanning would be indefensible. Verify by
      running `ci.ps1` and showing the Secret scan gate actually executing.
- [x] Confirm the real script trips gitleaks if it were ever staged, and that the template does not.

## Out of scope

- **Adding a `.env` loader to the backend.** Considered and rejected: a `.env` lives inside the
  repository directory, protected only by a `.gitignore` line, whereas the whole point here is a
  secret that cannot be committed because it is not in the tree. It would also duplicate the
  `appsettings → user-secrets → environment` chain the platform already provides, and dependency
  additions need their own justification (§8). Do not reopen this inside this card.
- Changing how `DatabaseAvailability` reads the variable. Reading the raw environment is correct
  and is what makes local and CI identical.
- Any change to `.github/workflows/backend-ci.yml`. CI supplies the variable from a service
  container and needs none of this.
- Making the integration tests **fail** rather than skip when no database is reachable. That is a
  defensible idea and a separate argument — raise it, do not implement it here.

## Notes for the implementing agent

Read `.agent/STATE.md` first and append to it last (§4.1). Then `backend/README.md`
"Configuration and secrets" and `backend/.gitignore` — both already encode this repo's position
on secrets, and this card extends it rather than inventing a new one.

The single most important property is the one that is easiest to get wrong: **the template must
stay committed while the real file cannot be.** Prove it with `git check-ignore -v`, do not assume
it from reading the `.gitignore`.

Bear in mind a real credential already exists for this variable and is in use — write the
template so that someone who already has one knows exactly where to put it.
