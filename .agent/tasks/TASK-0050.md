# TASK-0050 — Pupil entity, the pending-exclusion invariant, and the register read surface

Owner: backend-dev
Depends on: TASK-0039 (arms), TASK-0030 (assignment scopes — `pupil.view` is arm-scoped)
Contract impact: **additive** — `/pupils` read + biographical patch, `/admissions` queue,
`/pupils/duplicates`.
Status: queued

> **First of four pupil cards.** Spec 07 carries nine entities and 27 endpoints — far past §1's
> ~400-line dispatch rule. This card is the entity and its read surface. Registration-number issue
> is **TASK-0051** (blocked on TASK-0005c); child entities, the admission flow and bulk import
> follow. `ROADMAP.md` Phase 2 holds the sequence.

## Goal

The office can create a pupil record, find it again, and edit its biographical fields. Nothing can
reach `active` yet — that is admission approval, which needs a registration number, which needs
TASK-0005c. Every record this card creates is `pending`, and **`pending` means invisible
everywhere except the admissions queue.**

## Contract delta — additive

| Endpoint | Privilege | Notes |
|---|---|---|
| `GET /api/v1/pupils` | `pupil.view`, **arm-scoped** | Paged, filtered, scope-aware. **Excludes `pending` unless `status=pending` is passed.** |
| `GET /api/v1/pupils/{id}` | `pupil.view`, arm-scoped | Renders only what exists after this card — no contacts/health/documents blocks yet. |
| `PATCH /api/v1/pupils/{id}` | `pupil.update`, arm-scoped | Biographical only. **Rejects any attempt to set `registration_number` with 409.** |
| `GET /api/v1/admissions` | `pupil.view` | The pending queue, and the only surface that shows `pending`. |
| `GET /api/v1/pupils/duplicates` | `pupil.create` | Candidates by surname / first name / dob / contact phone, for admission step 1. |

`pupil` per **6.5.4's table** — read it there, it is not restated here. `registration_number` is
`null` while pending and this card never writes it. `age` is **derived, not stored** (whole years
as at the term end date). `blood_group`/`genotype`/`medical_note` are **not** on this entity —
6.5.4 says they moved to `pupil_health`, which is the next card.

## Acceptance criteria

- [ ] `pupil` table + migration per 6.5.4, `status` defaulting to `pending`,
      `registration_number` nullable and **uniquely** indexed (the unique index is TASK-0051's
      backstop per 6.5.10 — create it now so that card does not have to alter the table).
- [ ] **The pending-exclusion invariant, and it is the point of this card.** 6.5.14: "A pending
      pupil is excluded from every arm roster, every enrolment count, every capacity calculation,
      every score sheet, every result set, every weekly report, every report and every portal
      lookup. It exists in the admissions queue and nowhere else." Enforce it **where the query is
      built, not by each caller remembering** — a default-excluding specification or query filter
      that a caller must opt out of. Prove it: `GET /pupils` without `status` returns no pending
      record even when one matches every other filter, and `GET /admissions` returns it.
- [ ] **Arm-scoped `pupil.view` proven against real assignments** (TASK-0030's provider): a class
      teacher assigned to one arm sees only that arm's pupils; a school-wide holder sees all. Both
      directions, against the real `RoleAssignmentEffectivePrivilegeProvider`, not a fake.
- [ ] `PATCH /pupils/{id}` rejects a `registration_number` in the payload with **409**, tested.
      6.5.10: the number is immutable and "no ordinary edit path exists".
- [ ] `date_of_birth` validation gives an age between 2 and 20, with 6.5.4's **verbatim** rejection
      message: `A date of birth of 03/05/2024 makes this pupil 2 years old. Check the date.` —
      formatted with the real submitted date and computed age, not the literal example.
- [ ] `state_of_origin` accepts only the 36 states plus FCT — **free text is not accepted** (6.5.4:
      "this field is reported on and typed spellings make that impossible"). `lga` is validated
      against the selected state, not accepted free.
- [ ] Search (6.5.15) matches in one box: any part of surname/first/middle name, and **the
      registration number's serial alone — typing `41` finds `GRAS/2026/0041`**. Results report
      which field matched. Contact- and pickup-person search are the next card's; say so in the
      response shape rather than pretending to cover them.
- [ ] Default sort is class in progression order then surname ascending (6.5.15), page size 50.
      Cursor-paged on the existing `CursorPage<T>` convention — follow `ListAdminAccounts.cs`.
- [ ] Audit: every write records via the existing sink. **Ordinary pupil reads are NOT audited** —
      6.5.3 audits only safeguarding reads, which are the next card. Do not audit `GET /pupils`.
- [ ] `openapi.json` regenerated via `scripts/generate-openapi.ps1 -Promote`; `CONTRACT.lock`
      updated; diff additive only. All ten §9 gates green, `SUMMARY` pasted.

## Out of scope

- **Registration-number issue and the `registration_counter` table — TASK-0051**, which is blocked
  on TASK-0005c (the pattern, `serial_reset` and serial width live in settings and are not built).
  Create the unique index, write no counter, issue no number.
- **Every child entity — the next card.** `pupil_contact`, `pupil_health`,
  `authorised_pickup_person`, `barred_person`, `pupil_document`, `admission_record` (6.5.5–6.5.9).
  No safeguarding privilege enforcement, no audited reads, no document checklist.
- **The nine-step admission flow** (6.5.11) and its `POST/PATCH /admissions` write surface. This
  card ships the queue **read** only. `POST /admissions` step 1 belongs with the flow.
- **Status transitions** (6.5.14). Every one of them either issues a number, opens or closes an
  enrolment, or requires a reason tied to a flow that does not exist. `enrolment` is not built.
  Records stay `pending`; add no status-change endpoint.
- **Completeness percentage** (6.5.12), the list column and the incomplete-records report. It is a
  percentage across the *chased set*, which is entirely child-entity data. Omit the column rather
  than shipping a number that is always 0 or always 100.
- **Photograph upload** (`pupil.photo.update`, 9.6 derivatives), **bulk import** (6.5.13),
  **transfer**, **portal access history**, **enrolment/result/weekly history** on the detail view.
- Anything under `frontend/**`.

## Notes for the implementing agent

Read spec `07-module-pupils-guardians.md` §6.5.4, 6.5.14 and 6.5.15 — and §6.5.3 for the privilege
table. Skip 6.5.5–6.5.13; they are later cards and loading them will only tempt scope creep.

`Auth/AdminAccounts/ListAdminAccounts.cs` + its handler are the precedent for a filtered,
cursor-paged, privilege-gated, **scope-aware** list. TASK-0030 built the scope resolution — use
`IEffectivePrivilegeProvider`, do not re-derive an arm list.

**On the pending invariant.** This is the rule most likely to be quietly broken by a later card, so
build it as a structural default rather than a filter each query remembers to apply — the same
reasoning `UnitOfWorkBehavior` uses for "a failed command never half-commits". A later card adding
a pupil query must have to *opt out* to see pending records. If you find yourself writing
`.Where(p => p.Status != Pending)` in more than one place, that is the wrong shape.

**Do not model an enrolment.** 6.5.15's detail view lists enrolment history and 6.5.14's
transitions open and close enrolments, but that entity is a later card's. Leave the seam absent
rather than stubbed — a half-built `enrolment` is worse than none.

Size: if you pass roughly 1,000 lines of production code, stop and report.

**Gates.** `STATE.md` `## Gate commands` is the single home for the canonical invocation, its four
rules and the serialization requirement — follow it there. Stay in the turn until you have the
SUMMARY.
