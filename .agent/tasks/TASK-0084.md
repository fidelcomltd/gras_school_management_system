## The observation

Admins A and B are both Super Admins. A suspends B and B suspends A, and both requests start before either is awaited.
The expected result is exactly one 200 and one 409 `admin.last_active_super_admin`. Twice (2026-09-16, and 2026-09-18 on
TASK-0072's close gate, 1 of 1437) the result was **200 + 401** instead. Otherwise it passes.

## Hypotheses to confirm or kill, with evidence rather than argument

- **H1: the test is racy, and the product is right.** A's request commits B's suspension and revokes B's sessions before B's
  request has passed authentication, so B's request is rejected as unauthenticated. If so, 401 is the correct answer for
  a request from an account suspended mid-flight, and the test asserts one interleaving out of two legitimate ones.
- **H2: the product is wrong.** B had already passed authentication and was inside the handler (or waiting on the row lock)
  when it got the 401, for example because session validation re-runs after the lock, or because revocation surfaces as 401
  inside the transaction. That would mean a mid-operation logout where the spec promises the last-active check's 409.
- **H3: something else**, such as test-fixture session sharing, cookie jars, or clock-based session expiry.

## Acceptance criteria

- [x] Reproduce deterministically. Force each interleaving, for example with a test-only hook or barrier that holds one
      request at (a) before authentication and (b) after authentication, before the lock. Show which interleaving produces
      the 401. Do not rely on a loop of 1,000 runs as proof.
- [x] Say which hypothesis holds, citing the code path, file and line.
- [x] **If H1:** make the test deterministic and assert both legitimate outcomes explicitly, as separate tests per
      interleaving: 409 when both passed authentication, 401 when one was suspended first. Keep the spec's
      "only one succeeds" invariant: never two 200s, and never zero active Super Admins.
- [x] **If H2 or H3:** STOP after diagnosis and report the proposed fix before writing it. It touches authentication and
      sessions, so the orchestrator reviews the design first.
- [x] Whatever the outcome: the invariant "never zero active Super Admins" is asserted after every interleaving.
- [x] Gates: whole unit project; integration scoped to `AdminAccount|Session|Auth` on the local container, run at least
      3 times with zero failures. Never the full gate. Never push.

## Out of scope

Any other flaky test, and any change to the last-active-Super-Admin rule itself.
