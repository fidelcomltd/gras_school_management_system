## Goal

An administrator signs in and lands in a real back-office: a persistent navigation shell that
knows who they are, hides what their privileges do not allow, signs them out server-first, and a
working School Settings screen where they can read and edit the school's identity.

## Scope

**1. Authenticated shell** (`components/layout/`)
- Persistent nav (school name, current user, sign-out) plus a content region. The existing
  `AppShell` is the unauthenticated frame — extend or wrap it; do not fork a second shell.
- Nav items are driven by the caller's privileges from `GET /auth/me`. An item the caller cannot
  use is **absent**, not disabled-and-visible.
- Sign-out calls `POST /auth/sign-out` and only then clears client state. Clearing first is a §5
  blocker.

**2. Protected routing** (`app/router/`)
- A route guard: unauthenticated → sign-in; authenticated → the shell. Add paths to `paths.ts`
  as the existing file's comment instructs, and split the route table per-feature — it says to do
  that "once there is more than a handful", and this card crosses that line.
- A 403 screen for a route the caller's privileges do not permit, distinct from 404.

**3. School Settings screen** (`features/settings/`)
- Read `GET /settings` and render the identity fields.
- Edit via `PATCH /settings/identity` behind `settings.identity.update`, using react-hook-form +
  zod per `CONVENTIONS.md`, with server field errors mapped back onto the form.
- Success and failure feedback through the existing feedback components.

## Acceptance criteria

- [x] Sign-in → shell → sign-out round-trips against MSW handlers derived from the committed
      contract (`openapi-handlers.ts`), not hand-written response fixtures.
- [x] Nav renders only the items the mocked caller's privileges allow — asserted with two callers,
      one privileged and one not. **Absence asserted, not `disabled`.**
- [x] An unauthenticated visit to a protected path routes to sign-in; an authenticated visit to a
      path the caller lacks privilege for renders the 403 screen, not 404.
- [x] Sign-out proves the ORDER: the server call happens before client state is cleared. Assert the
      request fired, not just that state ended up empty.
- [x] Settings screen reads and renders `GET /settings`; a successful `PATCH` updates the view; a
      422 maps errors onto the right fields by name.
- [x] Every API call goes through `src/api/` — no raw `fetch`/`axios` outside it (§4.4 check 3).
- [x] `npm run verify` green with counts pasted, `Skipped: 0`.
- [x] `npm run test:e2e` — one Playwright spec covering sign-in → settings edit → sign-out.

## Notes for the implementing agent

Read `.agent/STATE.md` `## Layout`, then `.agent/rules/auth.md` and `.agent/rules/gates.md`,
then `frontend/CONVENTIONS.md` and `frontend/src/features/README.md`. `features/auth/` is the
existing pattern for a feature folder — follow its shape (`api.ts`, `components/`, `*-schema.ts`,
`*-screen.tsx`) rather than inventing a new one.

`src/app/router/app-router.tsx` currently inlines three routes and its own comment tells you to
split per-feature at this size. `components/layout/app-shell.tsx` is the only layout component.

**Auth is settled and is not yours to redesign** (`.agent/rules/auth.md`): HttpOnly
cookie session plus CSRF, single-flight refresh already implemented in `src/lib/http/`. All 401
variants are terminal — a reactive 401 goes to sign-in, never to `/refresh`. Do not add a token to
JS, do not compute expiry client-side, do not add a second refresh path.

Prefer finishing the whole card over polishing one part of it. If you run short, the settings
screen's edit path is the piece to cut — report it rather than shipping it half-tested.
