# TASK-0002 — Privilege register and authorisation enforcement

Owner: backend-dev
Depends on: —
Contract impact: additive (403 ProblemDetails response documented on protected routes; no

## Goal

Ship the authorisation substrate every later endpoint depends on: the immutable privilege
register, the scope model, server-side scope resolution, and the boot-time guard that makes a
forgotten privilege check a startup failure rather than a hole in production. When this is
done, no route can be added to the API without declaring the privilege it requires.

This deliberately ships **before** school settings, departing from `index.md`'s suggested build
order — see `STATE.md` Decisions 2026-08-26. It ships **without** login: authentication is
TASK-0003, which is signed off (HttpOnly cookie + CSRF) but not yet built. This card builds
against the existing `ICurrentUser` seam in
`SchoolManagement.Application/Abstractions/Identity/`, so it neither needs nor assumes a carrier.

## Contract delta

Additive only.

- Every protected route gains a documented `403 Forbidden` response returning RFC 9457
  `ProblemDetails` with a **generic** message and a stable error code. Per spec 9.2 the body
  must not reveal whether the target entity exists, and must not name the missing privilege.
- No existing `/api/v1/reference/*` or `/health/*` path changes shape. If the reference slice
  needs a privilege declaration to satisfy the boot guard, mark it explicitly anonymous rather
  than inventing a privilege for it.
- Regenerate `contracts/openapi.json` and `CONTRACT.lock` via
  `backend/scripts/generate-openapi.ps1 -Promote`. That script is the only sanctioned way those
  two files change.

## Acceptance criteria

- [x] All 93 privileges from `01-actors-and-privileges.md` §4.4.1 to §4.4.6 exist as immutable
      code-shipped constants, each carrying its `scopable` boolean exactly as the register
      states. Admins cannot create privileges. A test asserts the count and the scopable flags
      against the register so a future spec revision surfaces as a test failure.
- [x] `guardian.*` privileges are aliased to `contact.*` rather than broken
      (`02-data-model.md` §5.5 item 1).
- [x] Scope resolution implements §4.2.1 exactly: a request naming an arm resolves to that arm;
      naming a pupil resolves to the pupil's arm of record for the active term **from the open
      enrolment, never from a client-supplied arm id**; naming a result set resolves to that
      set's arm; naming a level with no arm requires the privilege school-wide.
- [x] The effective privilege set is resolved per request as the union of all active assignments,
      each tagged with the scope it arrived through (§4.2). Resolution itself is complete and
      tested (`PrivilegeDecision`, `IEffectivePrivilegeProvider`); the "assignments" side is a
      seam — see the log for why no `role_assignment` persistence exists yet.
- [x] Every route declares the privilege it requires and, where scopable, the route parameter
      that resolves the target arm. **A route with no declaration fails to register at boot**
      (spec 9.2) — covered by a test that adds an undeclared route and asserts startup throws.
- [x] Authorization fallback policy denies by default; anonymous access is opt-in and explicit
      (CLAUDE.md §5).
- [x] A failed check returns `403` with a generic body, and writes an audit event with outcome
      `rejected` (spec 9.2). Audit persistence may be a seam if the audit entity does not exist
      yet — if so, the seam is registered and tested, and a TODO carries this card's number.
- [x] Object-level checks run on reads as well as writes: a scoped holder requesting an entity
      outside their scope gets `403`, not a filtered empty result and not the entity.
- [x] Attempting to create an arm-scoped assignment for a role containing a non-scopable
      privilege is rejected at save time with the exact message in §4.2.
- [x] Tests: unit tests for scope resolution across all four resolution rules and for the
      escalation rejection; integration tests for anonymous, wrong-privilege, out-of-scope and
      in-scope against a route in each state. **Verified by the orchestrator against a real
      PostgreSQL (Skipped: 0)** — see the log for the one failure that run found
      (`SecureArmResponse` missing an OpenAPI example) and its fix.
- [x] `./backend/scripts/ci.ps1` green, output pasted, per the orchestrator's split of
      responsibility on the reopen: backend-dev applied the fix and verified locally

## Out of scope

- Login, logout, password hashing, session tokens, lockout — **TASK-0003**. The carrier is
  already decided (HttpOnly cookie + CSRF, `STATE.md` `## Auth decision`), so there is nothing
  for you to choose here — but do not implement any of it in this card either. Authorisation
  only: who may do what, not who they are.
- `admin_account`, `role`, `role_assignment` **persistence and CRUD endpoints**. This card needs
  the shapes to resolve scope; it does not need the management screens. If persistence is
  unavoidable to make resolution testable, add the entities and migrations but no endpoints, and
  say so in the log.
- The audit log module itself (spec 6.1.12) — seam only, per the criterion above.
- Any privilege check on a route that does not exist yet.

## Notes for the implementing agent

Read `.agent/STATE.md` first and append to it last (§4.1).

Read, in order: `product-specification/01-actors-and-privileges.md` §4.2 through §4.4 in full,
then `14-non-functional-requirements.md` §9.2, then `03-module-admin-roles-audit.md` §6.1.5 and
§6.1.7. §4.2 is the single most consequential decision in the admin module and §4.3's rationale
(a real incident where a head teacher moved a band boundary) explains why settings privileges
are separated — do not collapse that separation for convenience.

Follow the patterns already in the reference slice: `IEndpointModule` registration,
`ApiProblem`, `GlobalExceptionHandler`, `AuthorizationPolicies.cs`. `Security/` already has the
skeleton files.

The 93-constant register is bulk but low-risk; the reviewable logic is scope resolution and the
boot guard. If the total diff runs past ~400 lines because of the register, that is acceptable
— say so in the log rather than splitting the register across cards.

**Do not guess across the boundary.** If anything about the privilege register is ambiguous,
write the question into the card and stop. Do not invent a privilege the register does not list.
