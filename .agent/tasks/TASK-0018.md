# TASK-0018 — Make local-env.ps1 pass switches through to the gate script

Owner: backend-dev
Depends on: TASK-0016
Contract impact: none
Status: queued

## Goal

A developer can run the gate suite locally with any of `ci.ps1`'s switches. Today they cannot:
`./scripts/local-env.ps1 -GateArgs '-NoFailFast'` dies with

```
Cannot validate argument on parameter 'Configuration'. The argument "-NoFailFast" does not
belong to the set "Debug,Release" specified by the ValidateSet attribute.
```

because `$GateArgs` is a `[string[]]` splatted with `@GateArgs`, and splatting an ARRAY passes
positionally — so `-NoFailFast` binds to `ci.ps1`'s first positional parameter instead of being
read as a switch name. Pre-existing, but TASK-0016 made it bite: it added `-NoFailFast` and
`-AllowSkipped`, the two switches a local developer most needs, and `local-env.ps1` is the only
sanctioned way to run the suite with a resolved `POSTGRES_TEST_CONNECTION`.

Found by the orchestrator while independently verifying TASK-0016; the workaround used there was
to set the environment variable by hand and call `ci.ps1` directly, which defeats the point of
the wrapper.

## Contract delta

None. No file under `backend/src/**`, `frontend/src/**` or `contracts/**` changes.

## Acceptance criteria

- [ ] `./scripts/local-env.ps1 -GateArgs '-NoFailFast'` reaches `ci.ps1` as the SWITCH
      `-NoFailFast`, not as a positional `-Configuration` value.
- [ ] The same holds for `-AllowSkipped`, for two switches at once, and for a name/value pair
      such as `-Configuration Debug` — including the combination of both forms in one call.
- [ ] A wrong switch name still fails loudly at `ci.ps1`'s own parameter binding. Do not swallow
      unknown arguments to make the happy path work.
- [ ] Covered by the `backend/scripts/tests/` self-test harness TASK-0016 established, exercising
      the real argument path rather than asserting on a string.

## Out of scope

- Changing which gates run, their order, or any threshold.
- `ci.ps1`'s own parameters. They are correct; the wrapper is what mis-passes them.
- The credential-resolution logic (sources 1-4). It works and it is security-sensitive — read the
  header comment before touching anything near it, and prefer not to.
- Any CI workflow change. CI does not use this wrapper; it sets the environment variable itself.

## Notes for the implementing agent

Read the `.PARAMETER GateArgs` block and the invocation at the foot of `backend/scripts/local-env.ps1`
first. Splatting a HASHTABLE binds by name; splatting an array binds positionally — that asymmetry
is the whole bug. Whatever you choose, do not print or log the resolved connection string: the
header comment explains at length why this file never holds a realistic-looking credential, and
`.agent/drift/2026-Q3.md` (2026-09-04) records what happened last time a credential-shaped string
was committed into documentation.
