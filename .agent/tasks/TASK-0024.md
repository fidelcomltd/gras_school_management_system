# TASK-0024 — Pin the backend toolchain so CI and local cannot diverge

Owner: backend-dev
Depends on: TASK-0022 (which made these gates run at all)
Contract impact: none expected — but see the WARNING below
Status: queued

## Goal

`backend-ci` reproduces a local `ci.ps1` run exactly, because both use the same SDK and the same
gitleaks. The two analyzer findings that CI surfaced are fixed rather than silenced.

## Why this exists

TASK-0022 made the backend gates EXECUTE in CI for the first time. They immediately failed
8 of 10. **None of it is regression** — the backend has never actually passed CI. Two root
causes, four primary failures, six cascades:

| Failure | Cause |
|---|---|
| Format — `CA2025` at `PrivilegeAuthorizationTests.cs(209,34)` | `global.json` has `rollForward: latestFeature`, so CI installs a newer 10.0.x feature band than local's pinned 10.0.100. Newer SDK, newer analyzers. |
| Build — `CA1873` at `RequestLoggingBehavior.cs(78,17)` | Same. |
| Unit/arch + integration tests — `The argument <dll> is invalid` | Same SDK drift. xunit v3 runs on Microsoft.Testing.Platform and `dotnet test`'s VSTest-bridge argument handling differs across feature bands. |
| Secret scan — `leaks found: 15` | gitleaks **8.28.0** in CI vs **8.30.1** locally. Measured: same repo, same 21 commits, same config — 8.30.1 reports `no leaks found`, 8.28.0 reports 15. TASK-0011's `[[allowlists]]`/`regexTarget = "match"` fix is not honoured identically by 8.28.0. |

The remaining five (OpenAPI generate, integration tests, coverage, contract drift, and the
"tests were not skipped" assert) are cascades from Build failing.

- [ ] **CI prints `dotnet --version` before the gates run** so the SDK in use is never again a
      thing we infer. This is in `.github/workflows/backend-ci.yml`, which the ORCHESTRATOR owns —
      **request it, do not edit it.**

      `STATE.md`'s toolchain section so the next divergence is visible. **Confirm the secret scan

      lesson).
- [ ] **`CA2025` FIXED, not suppressed.** "Ensure tasks using `IDisposable` instances complete
      before the instances are disposed" is a genuine correctness risk — a task may touch a
      disposed object. Fix the lifetime; do not add a `#pragma` or a global suppression. If you
      conclude it is a false positive, argue it with evidence and stop.
- [ ] **`CA1873` FIXED, not suppressed.** Guard the expensive log argument (`IsEnabled`, or a
      source-generated logger message) rather than silencing the rule.
- [ ] **The `dotnet test` invocation works on the pinned SDK**, with the integration suite RUNNING
      (`Skipped: 0`). If pinning alone does not fix the `argument <dll> is invalid` error, the
      invocation itself needs adjusting for Microsoft.Testing.Platform — say so explicitly rather
      than working around it by changing what is tested.
- [ ] `./backend/scripts/ci.ps1` green locally, `SUMMARY` block pasted (§9).

  - `global.json`: `rollForward` changed `latestFeature` → `latestPatch`. `latestFeature` let CI

    This machine only has 10.0.100 installed, so I could not install CI's newer band locally to
    directly re-trigger the original failures under it — the fix is verified by SDK-resolution
    semantics, not by reproducing the failure and watching it disappear. Flagging this rather than
    claiming a repro I didn't have.
  - CA2025 (`PrivilegeAuthorizationTests.cs:209`, `SendAsAsync`): real bug, not analyzer noise.
    `using var request = new HttpRequestMessage(...)` sat inside a **non-async** method that
    `return`ed the `Task` from `_client.SendAsync(request, ...)` directly. Because the method body
    was synchronous, the `using` block's `Dispose()` ran the instant `SendAsync` returned its
    (still in-flight) `Task` — i.e. `request` could be disposed while `HttpClient` was still
    reading it. Fix: made the method `async` and `await`ed the call, so `Dispose()` is deferred by
    the compiler's state machine until the whole send completes. Before/after in the diff below.
  - CA1873 (`RequestLoggingBehavior.cs:78`, cancellation branch): the log call already goes
    through a `[LoggerMessage]` source-generated method (`BehaviorLog.RequestCancelled`), but that
    only skips the *internal* formatting/allocation when the level is disabled — the caller-side
    argument `(long)Stopwatch.GetElapsedTime(timestamp).TotalMilliseconds` is a plain C# method
    call passed as an argument, so it still runs unconditionally regardless of whether
    Information logging is enabled. (The success path a few lines up isn't flagged because it
    precomputes the same expression into a local `elapsed` variable first — but that only hides
    the eager evaluation from the analyzer, it doesn't skip it, so I didn't copy that pattern.)
    Fix: wrapped the call in `if (logger.IsEnabled(LogLevel.Information))` so the Stopwatch call
    itself is skipped when disabled — the analyzer-recognised, semantically real fix.
  - `dotnet test`: on the pinned 10.0.100 SDK (the only SDK on this box), unit+arch+integration
    all ran clean, `Skipped: 0` throughout — the `argument <dll> is invalid` failure did not occur
