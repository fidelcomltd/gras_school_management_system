# TASK-0019 — Idempotency substrate, then admin account management

Owner: backend-dev
Depends on: TASK-0003
Contract impact: additive (new endpoints) + a new request header on mutating routes
Status: queued

## Goal

A Super Admin creates, edits, deactivates and lists administrator accounts, with the invariants
spec 4.1 and 6.1.7 require. Because creating an account is retry-duplicable, this card first
builds the `Idempotency-Key` mechanism the project deferred in TASK-0013.

## Why the mechanism lands here

`STATE.md ## Known drift` carries a live trigger from TASK-0013's Option B deferral:

> **the first card implementing ANY retry-duplicable mutation builds the mechanism first** —
> §9.8.2's four named operations are examples, not the whole list.

A `POST` of an admin account is exactly that: a retried request that double-creates an
administrator is the failure the mechanism exists to prevent. TASK-0003 was narrowed so the
trigger would not fire there; it fires here. **Build the substrate first, in its own commit, then
the accounts on top of it.** If you find yourself implementing accounts first "to see the shape",
stop — that is how the deferral became permanent the first time.

Full record of what was deferred and what the implementing card must decide:
`backend/docs/ASSUMPTIONS.md` §2.14 and the 2026-09-04 entry in `.agent/drift/2026-Q3.md`.

## Contract delta

Propose and get approval BEFORE implementing (§3). Two parts.

**Part 1 — the header.** `Idempotency-Key` accepted on mutating routes: its shape, which routes
require versus merely accept it, and the error codes for a reused key with a different payload
and for a malformed key. This is additive to the routes TASK-0003 shipped; say explicitly whether
any TASK-0003 route gains it.

**Part 2 — the endpoints.** Admin account create / list / detail / edit / deactivate under
`/api/v1/admins` (or the name you justify), cursor-paginated per §9.5, deactivate-not-delete per
§9.4.

## Acceptance criteria

- [ ] `Idempotency-Key` mechanism exists and is applied once in the API layer, never per-endpoint.
- [ ] **Request fingerprinting**: a reused key with a different payload is rejected, not replayed
      against an unrelated response.
- [ ] **Stored-response replay**: a genuine repeat returns the original response, not a second
      creation.
- [ ] **Retention and purge rule under §9.9.** A stored key, fingerprint and response is itself
      personal data. An indefinite table is a defect, not a deferral — state the retention window
      and implement the purge.
- [ ] A test proves a duplicate `POST` with the same key creates exactly one account.
- [ ] Account create / list / detail / edit / deactivate, cursor-paginated (§9.5), deactivating
      rather than deleting (§9.4).
- [ ] **At least one active Super Admin exists at all times, enforced by the system** (spec 4.1) —
      with a test for the attempted-removal-of-the-last-one case.
- [ ] **Privilege escalation prevention** per spec 6.1.7, with a test per escalation path named
      there.
- [ ] Every endpoint is privilege-checked as server middleware; hiding a menu item is not
      enforcement (§9.2).
- [ ] Session tokens rotate on privilege change (spec 9.1). TASK-0003 built the rotation; this
      card is where a privilege change first actually happens, so prove it fires.
- [ ] Mutating routes are rate-limited, with a test that proves rejection.
- [ ] `./backend/scripts/ci.ps1` green with the integration suite RUNNING (`Skipped: 0`).
- [ ] Contract regenerated via `generate-openapi.ps1 -Promote`, `CONTRACT.lock` updated, new hash
      reported.

## Out of scope

- Admin account **screens**. Those follow once this API exists.
- Retrofitting `Idempotency-Key` onto TASK-0003's auth routes unless your delta argues for it —
  a repeated sign-in is not the same class of harm as a duplicated account.
- The audit log surface, unless spec 6.1 makes it inseparable from account mutation. If it does,
  say so in the delta rather than absorbing it silently.
