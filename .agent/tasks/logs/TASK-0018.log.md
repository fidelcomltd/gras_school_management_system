- 2026-09-04 backend-dev implemented. Fixed the tracked `backend/scripts/local-env.template.ps1`
  only (verified `local-env.ps1` untracked and never opened/read, so its credential was never
  touched). Root cause confirmed empirically before coding: splatting a `[string[]]` ALWAYS binds
  positionally in PowerShell, regardless of whether the array came from `-GateArgs`, from
  `ValueFromRemainingArguments`, or even from re-splatting a manually-populated automatic `$args`
  — only a genuinely engine-populated `$args` (unbound tokens, no named parameter in between) or a
  Hashtable splat binds by name. Since the card's acceptance criteria require the explicit
  `-GateArgs` interface, added `ConvertTo-SplattableGateArguments` (new function in the template):
  walks the flat token list, reading each `-Name` as a switch (`$true`) unless immediately followed
  by a token that does not itself start with `-` (then that token is its value) — no reflection on
  the target script, so an unknown name passes through unresolved and the GATE SCRIPT's own binder
  rejects it. Invocation changed from `& $scriptPath @GateArgs` to splatting the converted
  hashtable. `.PARAMETER GateArgs` doc comment and four new `.EXAMPLE` blocks added, one per
  required argument form.
  Self-test: new `backend/scripts/tests/local-env.tests.ps1` (same hand-rolled harness style as
  TASK-0016's `gate-summary.tests.ps1`, since this machine has only Windows-bundled Pester 3.4.0)
  plus a new fixture `backend/scripts/tests/fixtures/fake-gate.ps1` mirroring ci.ps1's real
  parameter shape (`[ValidateSet]` string, ranged int, three switches) INCLUDING `[CmdletBinding()]`
  — omitting that attribute was tried first and made PowerShell silently drop an unknown named
  argument instead of erroring, which would have made the wrong-switch-name assertion pass for the
  wrong reason. The harness runs the real tracked template as a genuine child `powershell.exe`
  process via a PowerShell source string (not a raw `-File` argv list — that re-parses each
  `-Xxx`-shaped array element as a new top-level parameter before the template even runs, a
  different quirk from the one this task fixes, and breaks the two-switches/name-value/combined
  cases before they reach the code under test). 21/21 assertions passed, exit 0.
  All four required argument forms verified working (single switch, two switches, name/value pair,
  both forms combined); a wrong switch name (`-Bogus`) fails at the FIXTURE's own
  `[CmdletBinding()]` parameter binder (`NamedParameterNotFound`), not swallowed, not misreported —
  confirmed the fixture's body never ran (no `Configuration=` echo) so it is a rejected bind, not an
  accepted no-op. `ci.ps1` itself, its parameters, and the credential-resolution sources 1-4 were
  not touched. No credential-shaped literal was added anywhere (checked by grep and by eye); the
  self-test asserts no run ever prints a `Host=...Password=...`-shaped line.
  Left undone: did not run the full `ci.ps1` suite through the fixed wrapper (card states no
  ci.ps1-green criterion; the self-test harness is the specified evidence and doing a full gate run
  is expensive and out of scope for this card). Did not modify the untracked `local-env.ps1`.

  Two things the agent found that are worth more than the fix itself, both cases of a test that
  would have passed for the wrong reason:
  (a) the fixture initially lacked `[CmdletBinding()]`, and PowerShell SILENTLY DROPS unknown
      named arguments in that case — so the wrong-switch-name assertion would have gone green
      against a binder that never rejected anything. The fixture now mirrors `ci.ps1`'s real
      `[CmdletBinding()]`. This is exactly the TASK-0016 lesson (a fixture must reproduce the real
      artefact's shape) reappearing in a different disguise.
  (b) invoking the template via a raw `-File` argv list re-parses each `-Xxx`-shaped element as a
      new top-level parameter before the template runs — a separate quirk from the one fixed here.
      The harness therefore runs via `-Command`, matching what a contributor actually types.
  Accepted limitation, recorded not carded: a parameter VALUE that itself starts with `-` would be
  misread as the next switch name. No `ci.ps1` parameter can take such a value (a two-member
  ValidateSet string, a non-negative int, three switches), and the `.PARAMETER GateArgs` block
  states the rule. Revisit only if a gate parameter ever accepts a negative number or a
  dash-leading string.
  No `ci.ps1`-green criterion on this card, deliberately — the self-test harness is the specified
  evidence and a full suite run was out of scope. `ci.ps1` parameters, the credential-resolution
  logic and the CI workflows are all untouched, as required.
