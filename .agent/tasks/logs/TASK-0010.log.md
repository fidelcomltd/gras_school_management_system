  **Root mechanism (verified directly, not guessed).** Read
  `Microsoft.Extensions.ApiDescription.Server`'s own `.targets` file
  (`~/.nuget/packages/microsoft.extensions.apidescription.server/10.0.10/build/...targets`). The
  target that actually writes the document is:
  `Target Name="GenerateOpenApiDocuments" Inputs="$(TargetPath)" Outputs="$(_OpenApiDocumentsCache)"`
  — i.e. MSBuild's own incremental-target check, comparing the compiled assembly's timestamp against
  one cache file in `obj/` (`SchoolManagement.Api.OpenApiFiles.cache`, which just lists the document
  paths `dotnet-getdocument.dll` wrote last time). **That check never looks at the generated document
  itself.** So if the document on disk is changed by anything other than this target running — a
  hand-edit, a stash pop, a file copied in from elsewhere — while the assembly and the cache file stay
  as they were, the target is (correctly, by its own contract) considered up to date and is skipped.
  `dotnet-getdocument.dll` never runs, the modified file is left exactly as it was, and the script
  reads whatever is now on disk and reports it as `==> Generated:` regardless.

  **Reproduced exactly as the card's table describes**, on this machine, before making any change:
  1. Confirmed clean baseline: `contracts/openapi.json` and `backend/artifacts/openapi/SchoolManagement.Api.json`
     both hashed `228ae57fd80c22f7e0511a665efce5d4722bb3280c66f5e3f4c96fff53795a65`.
  2. Hand-edited the artefact (`python -c "... del schema['example'] ..."`) to drop `SecureArmResponse`'s
     object-level `example` — same deliberate edit the card describes.
     Resulting file: **25807 bytes**, sha `6a5d51fef99afb956addf2245d96021c5be48e722a52bd3ce2642748802ac57d`
     — byte-for-byte the same size and hash the card reported.
  3. Ran `./scripts/generate-openapi.ps1` (incremental, `obj`/`bin` untouched). Build "succeeded", printed
     `==> Generated: ... (25807 bytes)`, but the file on disk was unchanged — confirmed the
     `GenerateOpenApiDocuments:` message block (which only appears when the target actually runs) was
     **absent** from the build log, and `obj/SchoolManagement.Api.OpenApiFiles.cache` /
     `bin/Release/net10.0/SchoolManagement.Api.dll` mtimes were identical before and after. The target
     was skipped, exactly as the mechanism above predicts.

  **The honest caveat, checked before sizing the fix.** Tested whether a realistic, non-hand-edit
  trigger reaches the same target-skip:
  - **A real source edit self-heals it.** With the artefact still corrupted from step 2, appended a
    trivial comment to `OpenApiExamples.cs` (no semantic change) and re-ran the script incrementally
    (no `obj`/`bin` deletion). The comment changed the source file's content, so the normal C# compile
    step correctly detected staleness, recompiled, gave the assembly a newer timestamp than the cache
    file, and the OpenApi target ran and rewrote the document correctly —
    **25138 bytes, sha `228ae57f...`**, self-healing the corruption with no hand-intervention. Reverted
    the comment afterward (working tree diff-clean against what was already staged).
  - **Branch switches and pulled changes to `OpenApiExamples.cs` behave the same way**: any real content
    change to a compiled input advances the assembly's timestamp past the cache file's, which is exactly
    what makes the target re-run. There is no path from "the source actually changed" to a stale
    document once the assembly rebuilds — the bug requires the *document* to be modified independently
    of a build.
  - **`ci.ps1`'s two builds do not interfere.** Traced it directly: the Build gate runs plain
    `dotnet build` (no `GenerateOpenApiContract` flag) — `_GenerateOpenApiDocuments`'s own condition on
    that flag means the OpenApi target never runs and the cache file is never touched during that gate.
    The Generate gate then runs `generate-openapi.ps1`, which is the *first* build in the run to pass
    `-p:GenerateOpenApiContract=true`; the cache file does not exist yet at that point (a fresh checkout
    has no `obj/`, and CI's `actions/cache` step only caches `~/.nuget/packages`, not `obj`/`bin`/
    `artifacts` — read `.github/workflows/backend-ci.yml` to confirm), so the target's `Outputs` are
    missing and it runs unconditionally on that first flagged build, every time. Confirmed live: the full
    `ci.ps1` run pasted below has exactly this two-build sequence and both the Generate gate and the
    drift gate passed clean. **Verdict: the two-build structure is not a contributor.** Record this so
    nobody re-investigates it.
  - **So: the only trigger found, hypothesized or reproduced, is a document modified by something other
    than the generation target itself** — a hand-edit being the concrete case reproduced here, with an
    interrupted build (partial write racing the cache bookkeeping) as a plausible but unverified sibling
    of the same class, not separately reproduced. Per the card's own instruction, sized the fix to match:
    **minimal**, not the "make CI clean-build everything" option the card explicitly rules out.

  **The fix — `backend/scripts/generate-openapi.ps1` only.** Before invoking `dotnet build`, delete both
  the generated document AND `src/SchoolManagement.Api/obj/SchoolManagement.Api.OpenApiFiles.cache`.
  Deleting the cache file is what matters: it is the target's actual tracked `Outputs`, so deleting it
  makes the target's up-to-date check fail unconditionally, forcing `dotnet-getdocument.dll` to run on
  every single invocation of this script regardless of whether the assembly needed recompiling. This
  also satisfies "must not report `==> Generated:` when it did not actually regenerate" by construction
  — regeneration is now unconditional, so the distinction the card warns about cannot arise.

  **Deleting the artefact alone is not sufficient — proved, not assumed.** Before settling on the fix
  above, tested the card's first-listed option in isolation: from a clean, in-sync `obj`/`bin`/artefact
  state, deleted only `backend/artifacts/openapi/SchoolManagement.Api.json` (left the cache file alone)
  and ran the unmodified script. The build "succeeded" but the OpenApi target was skipped (no
  `GenerateOpenApiDocuments:` block; cache/dll mtimes unchanged), so no document was written at all, and
  the script's own `Test-Path` guard correctly threw `Expected a document at '...' but none was
  produced.` That confirms the artefact's own presence/absence has no bearing on the MSBuild target's
  decision — only the cache file does. This is why the fix removes the cache file, not just the
  artefact (the artefact is also removed, defensively, so a build that somehow still failed to write it
  is caught loudly rather than silently reusing old content).

  **Fix verified with the exact same reproduction sequence.** From the fixed script: hand-corrupted the

  **The orchestrator's original framing was overstated and is corrected here.** This card was opened
  saying incremental and clean builds diverge from identical source, which reads as a routine hazard.
  The implementing agent read the actual `.targets` and established the real mechanism:
  `GenerateOpenApiDocuments` is declared `Inputs="$(TargetPath)" Outputs="$(_OpenApiDocumentsCache)"`,
  so its up-to-date check compares the compiled assembly against a bookkeeping file in `obj/` and
  **never looks at the generated JSON at all**. Any real source edit — even a no-op comment in
  `OpenApiExamples.cs` — advances the assembly past the cache and self-heals a corrupted artefact.
  Branch switches and pulled changes are therefore NOT triggers, and `ci.ps1`'s two-build structure
  does not interfere (verified live and by mechanism). The only confirmed trigger is a document
  modified outside the generation target.

  So the severity was lower than this card first claimed. The narrower finding that survives is still
  worth the fix, and is the part that actually cost time: the script could print `==> Generated:` over
  a document it had not written. It no longer can.

  Also proved, rather than assumed, that the obvious fix is wrong: deleting only the document leaves
  the cache current, the target still skips, and the build "succeeds" while writing nothing. Hence
  deleting the cache file — the target's real `Outputs`.

  Loose end left honestly open: interrupted-build-as-trigger was not separately reproduced
  (impractical to simulate a killed mid-write), noted as a plausible sibling the fix covers either way.
