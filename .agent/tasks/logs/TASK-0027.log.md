  **A real bug found and fixed along the way, not merely reported**: the raw `SqlQuery<T>` list
  query initially threw `42P18: could not determine data type of parameter` (a parameter appearing
  only in `IS NULL` context has no type to infer) and then `InvalidOperationException: required
  column 'created_at_utc' was not present` (EF's `SqlQuery<T>` resolves each expected column by
  running the SAME snake_case naming convention over the target type's property names — aliasing
  columns to PascalCase, matching the DTO field names, actually broke the lookup instead of fixing
  it). Both are recorded as repository-level implementation notes, not spec deviations.

  **The rate-limiter fix caught a real, non-obvious behavioural change**, found by running the full
  gate rather than trusting the new tests in isolation: the existing
  `SignIn_IsRejectedOnceTheSensitivePolicyLimitIsExceeded` test started failing after the fix, not
  because the fix was wrong but because it is now MORE correct — a successful sign-in sets the
  `__Host-Session` cookie, the test's `CookieJar` replays it on the next call, and with
  `UseAuthentication()` now running first that next call authenticates and partitions by ACCOUNT
  rather than by IP. Traced with a temporary response-header instrumentation (removed before
  finishing) rather than guessed at. Fixed by making that specific test use a deliberately wrong
  password (so it never authenticates and stays IP-partitioned throughout, which is what it is
  actually testing) — not by weakening the new ordering. The new
  `ChangePassword_PartitionsBySeparateAuthenticatedCaller_NotOnlyByRemoteIp` test is the one that
  would fail if this fix ever regressed to IP-only partitioning: two different authenticated
  accounts from one remote IP, independent budgets.

  **The finding worth carrying forward:** `ConcurrentDuplicatePosts_…` had, since it was written,
  asserted a scheduling accident — it demanded `[Created, Conflict]`, but two same-key requests have
  two legal shapes and which one occurs depends on whether the winner completes before the loser
  reads. Sixteen instrumented runs settled it: fifteen `[Created, Conflict]`, one (under full-suite
  load against hosted Neon) `[Created, Created]` with the second carrying `Idempotency-Replay: true`
  — and **exactly one row in all sixteen**. The substrate never double-executed; TASK-0019 has no
  defect. The test now accepts either shape, asserts the replayed body matches the winner's
  verbatim, and keeps the one-side-effect count unconditional. It was renamed
  `ConcurrentDuplicatePosts_ProduceExactlyOneSideEffect` — the old name promised the 409 that was
  never guaranteed.
