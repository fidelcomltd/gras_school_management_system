  **This is the FIRST run of this recurring card to add a line to the client seam** — eight prior
  runs added zero. The addition is justified and was proven, not assumed: `SuccessBody` resolved
  `never` for `ExportAuditEvents`, because the old `JsonOf` helper only matched an
  `application/json` content key and this operation declares `text/csv`. The agent demonstrated it
  with a throwaway probe (`error TS2322: Type '"occurredAtUtc,action
..."' is not assignable to
  type 'never'`) before writing any transport code, exactly as the card required. axios does not
  JSON-parse a `text/csv` body, so the payload really is a string at runtime and only the type was
  wrong. `client.ts` needed nothing; the change is one type-level helper in `client-types.ts`.

  **Orchestrator's own verification that the shared-file change is safe — this matters more than
  the green gates, because widening a type breaks nothing and so tests cannot prove it.**
  `ResponseBodyOf` matches `application/json` FIRST and only falls through when no JSON key
  exists, so it is byte-identical to `JsonOf` for any operation declaring JSON. Enumerated every
  2xx response in the contract that lacks `application/json`:

      jq over all 47 paths → exactly ONE match: GET /api/v1/audit-events/export → text/csv

  So the change provably cannot alter any other operation's response type — not "no test caught a
  change", but "no other operation can reach the new branch". `RequestBodyOf` still calls `JsonOf`
  unchanged, correctly, since every request body in this contract is JSON.


- 2026-09-10 **the agent's flagged `unwrap()` risk: INVESTIGATED AND NOT REACHABLE. No card
  needed.** It reported that `src/lib/http/request.ts`'s `unwrap()` treats any
  `response.data === ''` as a `204`-equivalent and returns `undefined` regardless of content-type,
  so a genuinely empty CSV body would mismatch the `string` type at runtime. Correct about the
  mechanism, and it rightly worked around it with a non-empty test body instead of reaching into
  `src/lib/http/` (outside this card's scope). **But the condition cannot arise:**
  `AuditEventCsvWriter.WriteAsync` writes the 13-column header line **unconditionally, before**
  iterating rows, so a zero-row export returns the header row — never an empty body. Verified in
  `backend/src/SchoolManagement.Api/Endpoints/AuditEventEndpoints.cs`.
  **Latent condition worth knowing, not worth a card today:** this becomes reachable the moment
  anyone makes that header line conditional on there being rows. Noted here so the connection is
  findable if that ever changes. Raising it was the right call — the workaround chosen was also
  the right one.
