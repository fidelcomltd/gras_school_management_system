  **Design decisions, all disclosed in `ASSUMPTIONS.md` §2.20, none of them redesigning the six
  inherited files**: privileges stored as a comma-joined `text` column (same technique
  `AdminAccountConfiguration.PasswordHistoryHashes` already uses for a newline-joined list) rather
  than a native Postgres array, since the exposed property is `IReadOnlyList<string>`-typed; the
  list's caller-chosen `sort`/`direction` needed a dynamic column name and comparison operator in
  raw SQL (`SqlQueryRaw`, not the fixed-order `SqlQuery<T>(FormattableString)` `AdminAccountRepository`
  uses), safe only because both are chosen from the query validator's own two-value whitelists,
  never from arbitrary caller text; `UpdateRoleRequest`'s "absent = unchanged" fields follow the
  existing `IsSuperAdmin`-style null-means-unchanged convention, with one necessary addition —
  `description` needs a THIRD state (leave alone / clear / set), resolved by letting an explicit
  empty string clear it (the entity already trims empty to `null`) while `null`/absent leaves it
  untouched, proven by a dedicated test; general create/update/delete audit events reuse the
  relevant `Privileges.Role.*` constant as the audit action (mirroring `UpdateAdminAccountCommandHandler`'s
  rule-4 precedent of reusing the error code as the action, rather than a new naming scheme).

  **Order of validation in both create and update, worth stating explicitly**: the entity is built
  (or mutated) FIRST — validating reserved name, field lengths, and privilege-registry membership,
  naming any unknown code as the offender — and the escalation guard runs SECOND, against the
  entity's now-canonical, alias-resolved privilege list. This means a genuinely unrecognised
  privilege code is always reported as `role.unknown_privilege`, never misreported as an escalation
  attempt (which would happen if the guard ran first against un-validated raw codes the actor could
  never legitimately hold). Update additionally snapshots `role.Privileges.ToArray()` BEFORE calling
  `SetPrivileges` — `Privileges` is a live view over the same backing list, so capturing it after
  mutation would make every requested code look "already existing" and silently defeat rule 2
  entirely. A rejected escalation on update still mutates the tracked entity in memory, but the
  unit-of-work's roll-back-on-failure guarantee (AGENTS.md §4, no explicit `SaveChangesAsync` in any
  handler) means nothing is persisted — proven by `Update_RuleTwo_...` reading the role back
  over HTTP afterward and asserting the pre-mutation privilege set, not merely asserting the 403.
