## Goal

`ci.ps1` gate 9 green for the right reason, and able to see the change it is gating.

## Two problems, one card

**1. Six findings, all the same fake string.** `gitleaks detect` reports six `generic-api-key`
hits on the fake `temporaryPassword` example TASK-0027 put in `OpenApiExamples.cs`, echoed into
`contracts/openapi.json` and `frontend/src/api/schema.d.ts`. Verified by the orchestrator
2026-09-06: commits `814b711` and `4170314`, both predating TASK-0028. Not a real credential.

**2. The gate cannot see the diff it is gating — this is the bigger one.** `gitleaks detect`
scans *committed history*. A dispatch runs the gates against an uncommitted working tree, so
gitleaks reads only what is already committed and the change under test is invisible to it. That
is why TASK-0027 closed with gate 9 green and TASK-0028 dispatch 1 found it red having touched
none of the flagged files: **the gate always fires one card late, against the previous card's
author.** This is the TASK-0011/0017 pathology again — a scan reporting PASS without having
examined the thing in question.

## Acceptance criteria

- [x] Gate 9 also scans the working tree (`gitleaks detect --no-git`, or `protect --staged`),
      so a secret introduced by the dispatch under test fails that dispatch and not the next one.
      A test proves it: plant a matching fake string in an uncommitted file, assert the gate fails.
      Done via `--no-git` (chose it over `protect --staged`: staged-only misses an uncommitted,
      unstaged file, the normal shape of a dispatch's own working tree). Proof:
      `backend/scripts/tests/secret-scan-working-tree.tests.ps1`, 3/3 assertions pass.
- [x] The six existing findings cleared **deliberately**, choosing between: a `.gitleaksignore`
      fingerprint entry per finding; changing the example string so it stops matching
      `generic-api-key`; or tightening the rule. Whichever is chosen, write down why in
      `backend/docs/ASSUMPTIONS.md` — TASK-0011 proved that an untested rule and an unexplained
      allowlist entry are the same defect wearing different clothes.
      Chose tightening the rule (a content-anchored `.gitleaks.toml` allowlist entry, Family C).
      Full reasoning, including why the other two are worse for this card: `ASSUMPTIONS.md` §2.19.
- [x] Do NOT blanket-ignore `contracts/openapi.json`, `schema.d.ts` or `OpenApiExamples.cs`. Those
      are exactly the files a real leaked example would land in.
      No path in any of the three is allowlisted anywhere; Family C matches only the one literal
      example string, verified not to swallow an unrelated planted secret in the same tree.
- [x] `ci.ps1`'s own self-test suite covers the new working-tree branch.
      `backend/scripts/tests/secret-scan-working-tree.tests.ps1`, new, same hand-rolled style as
      the two existing self-tests. Not yet wired into `.github/workflows/backend-ci.yml`
