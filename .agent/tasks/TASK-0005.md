## Goal

An administrator configures who the school is and how its registration numbers are formed, and
every such change is recorded as an immutable version rather than an overwrite. This is the
first product surface in the system and the substrate for everything that prints a result sheet:
the school name, logo, head teacher name and signature on a published sheet all come from the
configuration snapshot this card makes possible.

This is deliberately **not** the whole of module 6.2. The grading scale, assessment structure,
rating scales, trait lists, development domains and the fee notice are separate cards, because
6.2.13 replaces their seed data and they carry the two most expensive-to-reverse decisions in
the product (`25-open-conflicts-to-resolve.md` items 1 and 2).

## Acceptance criteria

- [ ] `school_profile` is a singleton with every field and validation rule in 6.2.3, including
      `timezone` fixed at `Africa/Lagos` and not editable in this version.
- [ ] Registration number configuration per 6.2.4: separator one of `/ - .` default `/`;
      `serial_width` 3–6 default 4; `serial_reset` `per_year` | `continuous` default `per_year`;
      `year_source` fixed at admission year and not editable.
- [ ] The preview endpoint composes from the current abbreviation, separator and width using the
      **next serial that would actually be issued** — `GRAS/2026/0040` with 39 pupils already
      admitted in 2026 — and recomposes from unsaved parameters without saving them.
- [ ] Reducing `serial_width` is rejected when an issued serial in the current counter exceeds
      the new width, with the exact message form in 6.2.10: `Serial 1043 will not fit in a width
      of 3. Choose 4 or more.`
- [ ] Changing the abbreviation requires the literal word `CHANGE` and a reason, writes an audit
      event, and **rewrites no already-issued registration number**. The response carries the
      count needed to build the 6.2.4 dialogue.
- [ ] The serial counter is keyed on **admission year alone**, not on the abbreviation, so a
      mid-year abbreviation change neither restarts the serial nor produces two pupils whose
      numbers differ only by prefix.
- [ ] Changing the abbreviation to a value used historically is allowed (6.2.11).
- [ ] `config_version` is append-only: every save to a versioned group writes a new row holding
      the whole serialised configuration, plus actor, timestamp, reason where required, and a
      monotonic version number. Nothing is overwritten.
- [ ] Optimistic concurrency on the config version. A stale save is rejected with the 6.2.11
      message, the first save wins, and **both attempts appear in the audit log**.
- [ ] Deleting the logo with no replacement is rejected: `A logo is required. Upload a
      replacement before removing the current one.`
- [ ] Uploads follow 9.6: content type verified by magic bytes not by extension or declared
      type, SVG rejected outright, EXIF stripped, stored outside the web root under generated
      names, served through an endpoint applying the parent record's privilege check, with
      `Content-Disposition` and `nosniff`.
- [ ] Explicit EF Core migration, reviewed, not auto-applied on startup.
- [ ] Tests per CLAUDE.md §6: every endpoint gets happy path, validation failure, unauthorized
      and not-found. Plus unit tests for serial composition, the width-reduction rejection, and
      the append-only guarantee of `config_version`.
- [ ] `./backend/scripts/ci.ps1` green, output pasted. Contract regenerated, lock hash matches.

  ### Idempotency declarations (Q2)

  None of this card's mutating routes create an independently-addressable new entity the way
  `POST /admins` does (no route in this card issues a registration number or any other identity a
  duplicate could collide with) — every one converges to the same final field values on a naive
  retry. What a retry *does* duplicate is a `config_version` row (and, once the audit seam is real,
  an audit event) — the same "duplicate audit-visible row, not duplicate business entity" class
  TASK-0019's Part 2 delta used to place `PATCH /admins/{id}` and `POST /admins/{id}/status` at
  **accepted**, not **required**. So:

  | Route | Idempotency-Key | Why |
  |---|---|---|
  | `PATCH /settings/identity` | accepted | Retry converges state; would double the `config_version` row otherwise. |
  | `POST /settings/identity/logo` | accepted | Same reasoning, plus an orphaned stored blob under the old generated name on a naive retry (the pointer just gets overwritten by the second call, harmless but wasteful). |
  | `POST /settings/identity/signature` | accepted | Same as logo. |
  | `PATCH /settings/abbreviation` | accepted | Same reasoning; also converges the audit-event count. |
  | `PATCH /settings/reg-number` | accepted | Same reasoning. |
  | `GET /settings/reg-number/preview`, `GET /settings`, `GET /config-versions(/{id})` | none | Reads, not mutations. |

  **Real gap found, not silently worked around:** `RequireIdempotencyKeyExtensions.BuildFingerprint`
  (TASK-0019) serialises the bound `IBaseCommand` via `JsonSerializer` to build the fingerprint. A
  multipart upload's bound argument won't carry the file's bytes through that path meaningfully, so
  `POST /settings/identity/logo`/`/signature` accepting the header needs the fingerprint to fold in
  a hash of the uploaded content, or a reused key against a genuinely different image would
  misclassify as a same-fingerprint replay instead of `idempotency.key_conflict`. Filed into
  `ASSUMPTIONS.md` §2.14 (edited this dispatch) as a decision TASK-0005b must make, not re-derived
  from scratch there. Not a contract-shape question — the header's declaration is identical either
  way — so it doesn't change the endpoint table.

  ### DB shapes

  - **`school_profile`** — singleton (fixed well-known id, enforced by convention: no create route,
    repository always upserts the one row). `school_name`, `short_name`, `address`, `phone`,
    `email`, `motto` (nullable), `head_teacher_name`, `logo_asset_id`/`signature_asset_id` (nullable
    FK to `stored_file`, filled by part `b`), `timezone` (fixed `Africa/Lagos`, stored so `GET
    /settings` can echo it; PATCH rejects any attempt to change it), `identity_version_number` (int,
    OCC pointer for the identity group), `abbreviation`, `abbreviation_version_number` (int, **own**
    OCC pointer — see next paragraph for why it's separate from identity's despite living in the
    same table).
  - Abbreviation shares the physical `school_profile` row (6.2.3 lists it as an identity field) but
    gets its **own** version-number column and its own privilege/endpoint, so an identity edit and
    an abbreviation edit never spuriously conflict each other's OCC check. Proposing two int columns
    on one table over two tables — happy to switch to a second singleton table if that reads
    cleaner; flagging the choice rather than silently picking.
  - **`stored_file`** (new, shared by logo/signature and any future upload field): `id`,
    `original_path`, `derivative_paths` (jsonb, empty for signature), `content_type` (sniffed, not
    declared), `size_bytes`, `uploaded_at_utc`. Files live outside the web root under generated
    names per §9.6; nothing in this table is served directly — only through the privilege-checked
    endpoints above.
  - **`registration_number_config`** — singleton, same convention as `school_profile`: `separator`,
    `serial_width`, `serial_reset`, `regnumber_version_number` (own OCC pointer, third independent
    group).
  - **`registration_number_counter`** — `admission_year` (PK), `last_serial_issued` (int). **This
    card creates the table and reads it (preview composition, width-reduction rejection) but does
    not write to it in normal operation** — nothing that issues registration numbers exists yet
    (pupil registration is a separate, later card, same seam-now/real-writer-later shape as
    idempotency's TASK-0019→TASK-0027 split). This card's own tests seed counter rows directly
    (e.g. a row at `2026 → 1043`) to exercise the width-rejection and preview logic without a real
    admission flow to produce that state.
  - **`config_version`** — **one global, append-only ledger**, not one chain per group: `id`,
    `version_number` (bigint, globally monotonic across every group, present and future), `snapshot`
    (jsonb — the WHOLE serialised configuration, every group's current values, not just the one
    that changed, per the card's note 1 and 6.2.9's snapshot rationale), `changed_group` (enum:
    `Identity | Abbreviation | RegistrationNumber`, extended by later cards), `actor_admin_id`,
    `reason` (nullable — populated only when the changed group's own rule requires one; see below),
    `created_at_utc` (`TimeProvider`, per `AGENTS.md` §2). Never updated, never deleted (purge is a
    separate, later concern, not this card's).
  - **Concurrency design, stated as a decision because there is no existing precedent to copy**
    (`SampleRecord` has no update command yet, so this is the first "edit something, detect a stale
    read" endpoint in the codebase — the shadow `Version` GUID convention from `ASSUMPTIONS.md`
    §2.4 exists for the auditing interceptor's own purposes but is never surfaced to a caller today).
    Proposed: `GET /settings` returns each group's current `versionNumber` (an integer read straight
    off `school_profile.identity_version_number` etc., NOT the shadow audit GUID). A `PATCH` echoes
    it back as `expectedVersion`. The handler, inside the same transaction that would insert the new
    `config_version` row, compares `expectedVersion` against the group's current pointer; a mismatch
    is `409` before anything is written, both the winning and losing save are what get recorded (the
    loser never gets a version row — only ever the audit-seam call, since it never actually wrote
    anything — matching 6.2.11's "both attempts appear in the audit log," not "both attempts get a
    config_version row"). This is an explicit design choice, not the generic EF shadow-property
    concurrency token, and I'd like it confirmed rather than built silently.
  - **Reason requirement, resolved from 6.2.10's table rather than assumed**: 6.2.10 states identity
    and registration-number edits are "Editable at any time" with no reason mentioned; only
    abbreviation's row says "Editable at any time with confirmation" (the `CHANGE` token) and 6.2.4's
    prose separately says the save "writes an audit event with a mandatory reason." So `reason` is
    required (non-empty) on `PATCH /settings/abbreviation` only, and null/not requested on the other
    two PATCH routes in this card. **6.2.9's generic "10-character reason" floor does not apply
    here** — its own prose scopes it to grading/assessment/traits/trait-scale/result-rules, none of
    which this card builds, and 6.2.10 confirms identity/abbreviation/reg-number are never subject
    to the published-results warning at all. Flagging as a genuine open question below rather than
    silently picking, since a human reading 6.2.4 in isolation might expect the 10-character floor
    to apply to abbreviation's reason too, for consistency.
  - **Audit seam gap found, not silently worked around**: both existing audit seams
    (`ISystemAuditSink`, `IAuthorizationAuditSink`) are shaped for actor-less or rejection-only
    events; neither has a slot for "this admin changed this group, here's the reason." This card
    needs an admin-attributed audit call to satisfy its own ACs ("writes an audit event", "both
    attempts appear in the audit log"). Proposing the smallest change: add an optional
    `actorAdminId` parameter to `ISystemAuditSink.RecordAsync` (default `null`, so TASK-0019's
    existing system-purge caller is untouched) rather than a third parallel interface. Internal-only,
    no wire/contract impact — noted here because it's a real gap, not because it needs approval at
    the contract layer.
