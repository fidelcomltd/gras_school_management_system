> **This card retires the project's oldest seam.** `LoggingAuthorizationAuditSink` and
> `LoggingSystemAuditSink` have both carried `TODO(TASK-0002)` since the first backend card, and
> both interfaces say in their own remarks that **one future card replaces both together, not just
> one.** This is that card. Do not replace one and leave the other.

## Goal

Every write against a governed entity produces one durable `audit_event` row (spec 6.1.12), in the
same transaction as the write where a write happened, and durably even where it did not. Both
logging seams are deleted. After this card the audit trail is real; before it, it is `ILogger`
output that nothing retains.

## Two rulings you are implementing, both HUMAN-SIGNED 2026-09-09

Read both entries at the top of `STATE.md` `## Decisions` in full before starting. In summary:

**1. The rejection path is separate, and this is the substance of the card.**
`UnitOfWork.ExecuteAtomicallyAsync` rolls back on a failure `Result`
(`UnitOfWork.cs:45-50` — `else { await transaction.RollbackAsync(token); }`). So:

- `outcome = success` → `context.AuditEvents.Add(...)`, **no `SaveChangesAsync`**.
  `UnitOfWorkBehavior` commits it with the change. Spec §9.3 satisfied by construction.
- `outcome = rejected` → written synchronously on a **separate short-lived connection** that
  commits immediately, so it survives the rollback of the command that was rejected.

**Why this is the whole point.** TASK-0030's escalation-rule tests assert against a
`RecordingSystemAuditSink` fake that has no transaction, so a literal §9.3 implementation leaves
every one of them GREEN while production loses every rejection record — the exact defect class
Phase 0b existed to kill. **Prove the rejection path against Postgres, not against a fake.**

**2. Append-only at both layers** — migration `REVOKE`, plus no update/delete path on the
repository, held by an architecture test. The administrative pruning role is NOT provisioned on Neon
or in CI: accepted drift, already recorded. Do not provision it; do not let its absence block you.

## The table — spec 6.1.12

**All thirteen fields with their exact types, lengths and nullability are in spec 6.1.12's table.
Read it there; it is not restated here.** The four things that table will not tell you:

- `id` is `bigint` identity (BIGSERIAL). **Not** a GUID and not the `Guid` v7 the rest of the
  schema uses — 6.1.12 wants it monotonic so ordering is unambiguous inside one millisecond.
- `actor_label` is captured **at write time**, not joined on read. That is the whole reason the
  column exists: the row must stay readable after the account is renamed or deleted.
- `source_ip` is **truncated to /24 for IPv4 and /48 for IPv6 before storage**, never stored full.
  This is a PII rule (§8), not a nicety — truncate before the value reaches the entity.

## Notes for the implementing agent

Read spec `03-module-admin-roles-audit.md` §6.1.12 and `14-non-functional-requirements.md` §9.3 in
full — they are short and they are the whole specification. Then read
`Application/Abstractions/Audit/ISystemAuditSink.cs` and
`Application/Abstractions/Authorization/IAuthorizationAuditSink.cs`: both remarks blocks tell you
they are seams to be replaced together, and they are the closest thing to a design brief you have.

`Behaviors/UnitOfWorkBehavior.cs` and `Infrastructure/Persistence/UnitOfWork.cs` are the two files
ruling 1 turns on. Read them before designing anything.

For the separate rejection connection: the project configures `EnableRetryOnFailure`, and
`UnitOfWork`'s own comment explains why a user-initiated transaction must sit inside
`strategy.ExecuteAsync`. Your rejection writer needs the same discipline on its own connection —
do not hand-roll a raw `NpgsqlConnection` that bypasses the execution strategy.

**Do not create a third audit abstraction.** Two interfaces exist; keep two, or narrow to one if
one genuinely serves both — but do not end up with three, the way TASK-0030 was told not to create
a third guard type.

Size: this is a big card. If you pass roughly 1,200 lines of production code, **stop and report**
rather than pushing on. The read surface is already split out and the before/after backfill is
already scoped out, so an overrun means something else grew and I would rather split again.

**Gates.** `STATE.md` `## Gate commands` is the single home for the canonical invocation, the four
invocation rules, and the serialization requirement — read it there and follow it exactly; it is
not restated here. Two points that bear on this card specifically: **stay in the turn until you
have the SUMMARY**, and while iterating use `dotnet test --filter`, because a bare `dotnet test`
skips every integration test and exits 0 — which on this card would skip precisely the
Postgres-backed rejection-durability tests that are its entire point.

**On flaky failures:** socket drops, `No such host is known`, or disjoint failure sets across runs
are hosted-Neon/network flakes, not your code — report them as such. A `23505 duplicate key`
together with `Sequence contains no elements` in one run means a concurrent gate run; I will not
start one against you.
