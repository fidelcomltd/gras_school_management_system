# TASK-0012 — Declare the problem-detail extension members in the contract

Owner: backend-dev, then frontend-dev (sequenced)
Depends on: —
Contract impact: additive
Status: queued

## Goal

Every error response this API sends carries `errorCode` and `traceId`. The contract declares
neither, and forbids both. A client that does what the schema's own description tells it to do —
"Branch on the `errorCode` extension member" — cannot, because the generated type has no such
member. Fix the contract so the two members clients are told to depend on are declared.

## The finding (TASK-0001 finding B1, verified twice)

`contracts/openapi.json`, `components.schemas.ProblemDetails` and `HttpValidationProblemDetails`:

- both declare `"additionalProperties": false`
- `ProblemDetails` declares exactly `detail, instance, status, title, type` — no `errorCode`, no
  `traceId`
- both `example` objects DO contain `errorCode` and `traceId`, so **each example is invalid against
  the schema that illustrates it**

Meanwhile the API attaches `errorCode` to every problem response
(`Http/ResultExtensions.cs:75`, `Http/GlobalExceptionHandler.cs:117`) and `traceId` centrally to all
of them, framework-generated ones included (`Program.cs:132`).

Root cause: `Program.cs:93` sets `UnmappedMemberHandling.Disallow` globally, so the generator stamps
`additionalProperties: false` on all nine schemas. Right for request bodies, wrong for RFC 9457
problem objects, where extension members ARE the mechanism.

Already propagated to the client: `frontend/src/api/schema.d.ts:292` emits a five-member
`ProblemDetails` with neither extension.

## Contract delta

Additive. Both problem schemas gain two declared members:

| Member | Type | Notes |
|---|---|---|
| `errorCode` | string | Stable, machine-readable. Clients branch on this, never on `detail`. |
| `traceId` | string | Correlation id to quote in a support ticket. |

Two decisions to make and state in this card before implementing:

1. Whether the schemas keep `additionalProperties: false` with the two members now declared
   (recommended — they stay closed and the members become part of the contract) or relax to open.
   Either way, do not change the other seven schemas.
2. Whether `required` is the right expression of "always present", judged against how
   `openapi-typescript` emits it. The goal is that `problem.errorCode` type-checks in frontend code
   without a cast. Say what you chose and why.

## Acceptance criteria

- [ ] No hand edit to any generated file.

## Out of scope

- Relaxing `UnmappedMemberHandling.Disallow` globally. It is correct for request bodies, and
  changing it to fix a response-shape problem has a far larger blast radius. If you conclude the
  global setting must change, stop and raise it.
- The other seven schemas.
- How errors are produced. The behaviour is right; only its declaration is wrong.
