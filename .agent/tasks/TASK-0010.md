# TASK-0010 — Make OpenAPI document generation deterministic

Owner: backend-dev
Depends on: TASK-0009 (closed)
Contract impact: none — the correct document is already committed
Status: done

## Goal

An **incremental** build can produce an OpenAPI document that differs from what a **clean** build
produces, from identical source. Since `contracts/openapi.json` is build output and the drift gate
compares against it, a non-deterministic generator undermines the whole contract mechanism: the
document is only trustworthy if the same source always yields the same bytes.

## Reproduction, observed 2026-08-26 by the orchestrator

Source contained the `SecureArmResponse` example the whole time — verified in
`backend/src/SchoolManagement.Api/OpenApi/OpenApiExamples.cs` (present, `[typeof(SecureArmResponse)]`).

| Step | Result |
|---|---|
| Hand-edit the git-ignored artefact `backend/artifacts/openapi/SchoolManagement.Api.json` to drop the object-level `example` | (deliberate, for a negative test) |
| `./scripts/generate-openapi.ps1` (incremental build) | artefact **25807 bytes**, object-level `example` **ABSENT**, sha `6a5d51fe…` |
| `./scripts/ci.ps1` | `FAIL: OpenAPI contract drift` and `FAIL: Tests` (`EverySchema_HasAnExample`) — both correct, both reacting to a wrongly-generated document |
| `rm -rf src/SchoolManagement.Api/{obj,bin}` then `./scripts/generate-openapi.ps1` | artefact **25138 bytes**, `example` **PRESENT**, sha `228ae57f…` — **byte-identical to the committed contract** |

So the committed contract was right, the source was right, and the tests and drift gate were right
to complain. The generator was wrong, and only because the build was incremental.

Note the script prints `==> Generated: …` in both cases. It reports success identically whether or
not the document was actually regenerated from current source, which is what made this take an hour
to pin down.

## An honest caveat on the reproduction

The orchestrator's sequence **began with a hand-edit** of the artefact, which made its modification
time newer than the assembly. That is the most likely trigger and it is not a normal developer
action. Establish the real blast radius before deciding how hard to fix:

- Does a realistic scenario reproduce it — switching branches, an interrupted build, pulling changes
  that touch `OpenApiExamples.cs`, or `ci.ps1` building twice with different properties?
- If the ONLY trigger is a hand-edited artefact, severity drops sharply and a minimal fix (delete
  before generate) is enough. **Say so plainly if that is what you find** — do not inflate it to
  justify a larger change.
- Either way, one part stands regardless of trigger: the script printed `==> Generated:` while not
  actually regenerating. A command that reports work it did not do is worth fixing on its own.

## Which way this fails

Both directions are ultimately caught, which is why this is a correctness-of-tooling card rather
than an emergency:

- **False alarm:** a stale build produces a wrong document, the drift gate fails, and a developer is
  sent to debug a contract change that never happened. Costly and confusing.
- **Wrong promotion:** someone runs `-Promote` off a stale build and commits a document missing
  examples. `EverySchema_HasAnExample` then fails, so it does not reach `main` silently — but only
  because that test exists, which is a thin margin for the "single source of truth for every byte
  crossing the HTTP boundary" (§3).

## Acceptance criteria

- [x] Document generation is deterministic: from identical source, an incremental build and a clean
      build produce byte-identical documents. Likely fixes, in order of preference — delete the
      artefact before generating so a stale file cannot be mistaken for fresh output; and/or force
      the document-generating build to not reuse stale outputs. Choose one and explain why.
      **Fixed by forcing regeneration, not merely by deleting the artefact — see Log for why deleting
      the artefact alone was proven insufficient.**
- [x] **Reproduce the failure first**, then show it fixed. Follow the table above to get a stale
      state, confirm you can reproduce the wrong output, apply the fix, and show the same sequence
      now yielding `228ae57f…`. A fix without a reproduction is a guess.
- [x] `generate-openapi.ps1` must not report `==> Generated:` when it did not actually regenerate,
      or must make regeneration unconditional so the distinction cannot arise.
- [x] Investigate whether `ci.ps1` building twice — once in the Build gate without
      `GenerateOpenApiContract=true`, once in the Generate gate with it — contributes. If the two
      builds interfere, say so; if not, say that too, so the next person does not re-investigate.
      **They do not interfere — see Log.**
- [x] `./backend/scripts/ci.ps1` green apart from the known SSH.NET gate (TASK-0007). Paste it.
- [x] Committed contract must still hash to
      `228ae57fd80c22f7e0511a665efce5d4722bb3280c66f5e3f4c96fff53795a65` when you finish. This card
      fixes tooling; it must not change the contract. **Never run `-Promote` from a build you have
      not verified is clean** — that is precisely the failure being fixed.

## Out of scope

- The SSH.NET advisory (TASK-0007).
- Changing what goes *into* the document — no new examples, descriptions or schema changes.
- Reverting TASK-0009. Its ci.ps1 restructuring is sound and its tests are correctly placed; this is
  a pre-existing generator issue that TASK-0009 merely gave more surface to.
- Making CI clean-build everything as a workaround. That hides the non-determinism behind a slower
  pipeline instead of fixing it, and leaves local runs still wrong.

## Notes for the implementing agent

Read `.agent/STATE.md` first and append to it last (§4.1).

`Microsoft.Extensions.ApiDescription.Server` generation is opt-in here via
`GenerateOpenApiContract=true` (see `SchoolManagement.Api.csproj` — deliberately not on every
build). Its MSBuild target likely has an up-to-date check comparing the output document against the
assembly; a hand-touched or externally-modified artefact can therefore look newer than its input and
suppress regeneration. That is a hypothesis from observed behaviour, not a conclusion — verify it
before fixing against it.

The property that matters is simple to state and worth stating in a comment wherever you fix it:
**the same source must always produce the same document.** Everything in §3 depends on it.

  **Root mechanism (verified directly, not guessed).** Read
  `Microsoft.Extensions.ApiDescription.Server`'s own `.targets` file
  (`~/.nuget/packages/microsoft.extensions.apidescription.server/10.0.10/build/...targets`). The
  target that actually writes the document is:
  `Target Name="GenerateOpenApiDocuments" Inputs="$(TargetPath)" Outputs="$(_OpenApiDocumentsCache)"`
  — i.e. MSBuild's own incremental-target check, comparing the compiled assembly's timestamp against
  one cache file in `obj/` (`SchoolManagement.Api.OpenApiFiles.cache`, which just lists the document
  paths `dotnet-getdocument.dll` wrote last time). **That check never looks at the generated document
  itself.** So if the document on disk is changed by anything other than this target running — a
  hand-edit, a stash pop, a file copied in from elsewhere — while the assembly and the cache file stay
  as they were, the target is (correctly, by its own contract) considered up to date and is skipped.
  `dotnet-getdocument.dll` never runs, the modified file is left exactly as it was, and the script
  reads whatever is now on disk and reports it as `==> Generated:` regardless.

  also satisfies "must not report `==> Generated:` when it did not actually regenerate" by construction
