# TASK-0055 — Add the `entityId` filter to the audit log read surface

Owner: backend-dev
Depends on: TASK-0049 — closed 2026-09-09. Nothing else blocks this.
Contract impact: **additive** — one new optional query parameter on two existing operations. No new
path, no new schema, no shape change to anything already published.
Status: done

## Goal

An `audit.view` holder can filter the audit log to **one entity's** trail, which is spec 6.1.12's
actual motivating scenario: "a parent comes to the office in March insisting their child scored 62
in Mathematics and the sheet says 26." Today `entityType=pupil` narrows to *every* pupil, so that
question cannot be asked. `entity_id` is already stored and already returned on `AuditEventDto` —
only the filter is missing.

## Why this card exists

TASK-0049 shipped the five filters its own contract-delta table named, and `backend-dev` correctly
declined to invent a sixth, flagging the tension instead (§1: do not invent product behaviour).
The orchestrator confirmed the gap was real and escalated it as open question 14.
**Resolved 2026-09-09 by the human: add it.** This card is that decision.

## Contract delta — additive

One optional query parameter, `entityId`, on **both** existing operations:

| Operation | Route |
|---|---|
| `ListAuditEvents` | `GET /api/v1/audit-events` |
| `ExportAuditEvents` | `GET /api/v1/audit-events/export` |

- Type `string`, optional, **exact match** — symmetric with the existing `entityType` and `action`
  filters, which are also exact-match strings. Not a prefix, not a `LIKE`, no normalisation.
- `AuditEvent.EntityId` is already `string?` in the domain, so no conversion is needed and none
  should be added. Root §8: IDs are opaque strings across the wire.
- Combinable with all existing filters, as they are with each other.
- **No new path and no new schema.** Path count must remain **47**. If it moves, something widened
  that should not have.

## Acceptance criteria

- [x] `entityId` added to `ListAuditEventsQuery` and `ExportAuditEventsCommand`, threaded through
      to `AuditEventQueryRepository.ApplyFilters` as one more `if (entityId is not null)` clause
      alongside the existing five. **Both** `ListAsync` and `StreamAsync` get it — the export
      honouring a filter the list does not (or vice versa) is the bug to avoid here.
- [x] A test filtering by `entityId` alone.
- [x] A test combining `entityId` with `entityType` and asserting the **intersection** — two rows
      sharing an `entityId` but differing in `entityType` must not both come back. Follow
      `List_Filters_CombineAsAnIntersectionNotAnUnion`'s existing shape; do not weaken it.
- [x] **The export's self-audit row records `entityId` too.** `BuildFilterMetadata` currently
      writes six keys; it must now write seven, with the key present-but-null when unfiltered, so
      that an unfiltered export and a one-entity export stay distinguishable. **This is the point
      of the whole card** — TASK-0049's "exporting one pupil's rows must be distinguishable after
      the fact" criterion was only half-satisfiable without this filter. Assert it by reading the
      log back after an export, as that card's test does.
- [x] `openapi.json` regenerated via `scripts/generate-openapi.ps1 -Promote`; `CONTRACT.lock`
      updated; **still 47 paths**; diff additive only. Report the new hash.
- [x] Verify with `dotnet test --filter` over what you touched, plus `dotnet build -warnaserror`
      and `dotnet format --verify-no-changes`. Report exact counts.

## Out of scope

  `after_json`, no `sourceIp` filter. If one is wanted it is a separate decision.
- **Frontend.** TASK-0054 regenerates the client and is deliberately sequenced *after* this card so
  the client is generated once against a contract carrying all nine parameters.
- **The CSV formula-injection fix** — that is TASK-0053, independent of this.
- Anything under `frontend/**`.

## Notes for the implementing agent

This is a small, highly patterned change. `ApplyFilters`, `ListAuditEventsQuery`,
`ExportAuditEventsCommand`, `BuildFilterMetadata`, the two endpoint parameter lists, and the
generated document. Expect well under 150 production lines; if you pass that, stop and report,
because the shape suggests something has been misread.

Read `ListAuditEvents.cs` and `AuditEventQueryRepository.ApplyFilters` first and copy their
existing idiom exactly — the point of this card is symmetry with what is already there, not a new
convention.

**Do not add validation on `entityId`'s format.** It is an opaque string that spans several entity
types (Guid-shaped today, not guaranteed to stay so), and a format rule would reject legitimate
future values. The existing `entityType`/`action` filters have no format validation either.

**Gates.** `STATE.md` `## Gate commands`: the **orchestrator** runs `ci.ps1`, once, backgrounded.
You verify with `dotnet test --filter` over what you touched and stop. Do not run the full gate.
