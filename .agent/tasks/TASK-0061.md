## Goal

`GET /pupils` returns pupils in 6.5.15's class-progression order — level order, then arm, then
surname, then id — instead of today's surname-then-id. This is the half of 6.5.15 that has been
live drift since 2026-09-09, deferred out of TASK-0059 as its pre-authorised cut line.

## Contract delta

None. See header.

## The ruling — where a pupil with no open enrolment sorts

**Ruled by the human on 2026-09-15: LAST.** One flat trailing block after every class, ordered
surname then id. Full reasoning and the three rejected options: `decisions/2026-Q3.md`, same date.

Three parts of the ruling bind the implementation:

1. **No sub-grouping by status inside the block.** Do NOT order transferred, then withdrawn, then
   graduated. 6.5.15's `status` column already carries that, and every extra sort key is one more
   cursor field and one more page seam to get wrong.
2. **Use a NON-NULL sentinel, not a NULL.** Give the unenrolled a max level ordinal and an empty
   arm key so the widened keyset `(levelOrdinal, armOrdinal, surnameKey, id)` stays a straight
   tuple comparison. A NULL in the keyset comparison is exactly the seam bug criterion 4 hunts.
3. **A default `status` filter is NOT in this card.** If leavers on the register turn out to be
   unwanted, that is a visibility change, it is contract-visible, and it gets its own card.

**Who this actually affects:** `transferred`, `withdrawn` and `graduated` pupils — plus the
`pending → withdrawn` lapsed application of 6.5.14, which never held an enrolment at all. `pending`
is NOT in scope: TASK-0050's model-level query filter already excludes it from the register.

## Acceptance criteria

- [x] Unenrolled pupils sort last, as one flat block ordered surname then id, per the ruling above.
      No sub-ordering by status.
- [x] Default sort is level order, then arm, then surname, then id, per 6.5.15.
- [x] **Pagination stays keyset/cursor, never offset** (9.5). The cursor must widen to carry the new
      sort keys; a sort that silently degrades to offset paging fails this card.
- [x] The widened cursor carries no NULL sort key — sentinel values, per ruling part 2.
- [x] A test proving stable ordering ACROSS a page boundary — **passes, but seeds ASCII-only surnames, so it cannot see the collation seam defect found at review; see TASK-0068** — the bug a widened cursor actually
      causes is a row repeated or skipped at the seam, which a single-page test cannot see.
- [x] A test covering the unenrolled case, seeding BOTH shapes that produce it: a pupil whose
      enrolment was closed (`transferred`/`withdrawn`/`graduated`) and a `pending → withdrawn`
      record that never had one.
- [x] The `pending`-exclusion invariant still holds everywhere except the admissions queue.
- [x] **The admissions queue is BYTE-FOR-BYTE unaffected** — `ListAdmissionsQueueAsync` still orders
      surname-then-id and still round-trips the cursor format it emits today. See the shared-cursor
      warning in `## Notes`; this is the regression this card is most likely to cause.
- [x] `openapi.json` regenerated and unchanged.

## Out of scope

- Client-selectable sort orders. 6.5.15 defines the default; alternatives need their own card.
- A default `status` filter on the register. See ruling part 3.
- Any change to the pupil response shape.

## Notes for the implementing agent

The existing keyset cursor from TASK-0050 is the thing most likely to bite: widening a cursor is
where off-by-one page seams come from, hence the across-page-boundary criterion above. Its current
shape is `(surnameKey, id)` in `PupilListCursor.Encode`; today's ordering is
`PupilRepository.ListAsync`, `.OrderBy(p => p.Surname.ToLower()).ThenBy(p => p.Id)`.

**THE TRAP, found by the orchestrator at dispatch — read this before you touch `PupilListCursor`.**
That cursor type is **shared by TWO methods**, and only one of them is yours:

| Site (`Infrastructure/Persistence/Repositories/PupilRepository.cs`) | This card |
|---|---|
| `ListAsync` — `.OrderBy` at ~line 101, decode at ~line 85 | **YES — widen this one** |
| `ListAdmissionsQueueAsync` — `.OrderBy` at ~line 132, decode at ~line 117 | **NO — must not move** |

`ListAdmissionsQueueAsync` lists `Status == Pending`, and this card puts `pending` explicitly out
of scope. Every pending pupil is also unenrolled by definition, so widening its sort would collapse
the whole queue into the sentinel block for no gain — and because both methods call the SAME
`PupilListCursor.TryDecode`/`Encode`, changing that type in place silently changes the queue's
cursor format too. TASK-0064 shipped the `/admissions` screen against that format three commits ago.

So: **do not widen `PupilListCursor` in place.** Add a separate wider cursor type for the register
(e.g. `PupilRegisterCursor`) and leave `PupilListCursor` and the queue path untouched, or make the
widening provably opt-in per call site. Whichever you choose, the acceptance criterion above wants a
test that the queue's ordering and cursor round-trip are unchanged.

Level order comes from `class_level`'s progression chain (`next_level_id`, TASK-0038's eight rules),
not from alphabetical level names — "Primary 10" must not sort between "Primary 1" and "Primary 2".

The same widened ordering must hold for an arm-scoped caller (TASK-0059's `allowedArmIds` path),
not just the unrestricted one.
