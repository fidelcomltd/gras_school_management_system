## The constraint that rules out the obvious fix

The gate runs `gitleaks detect` **without `--no-git`, so it scans history**. Every finding above
carries a commit hash. Editing or deleting the offending lines today will NOT clear the gate — the
strings stay reachable in `faa8e1c` and `5a2cb1c`. Do not rewrite published history to fix a
scanner finding on a fake credential; that trade is not worth it.

## Decision — made 2026-09-04 by orchestrator. Implement it; do not re-litigate.

**A fingerprint-pinned `.gitleaksignore`.** Five entries, the fingerprints listed above, one per
line, each with a comment naming what it is and why it is not a secret.

Verified before deciding: the real credential the developer keeps outside the repo shares
**neither host nor password** with any committed string, so all five findings are invented and
nothing real is exposed. That check has been done — do not repeat it, and never read or echo that
file.

Rejected: a `targetRules`-scoped path allowlist over `.agent/tasks/**`. It would blind the rule to
that whole subtree — the one place agents paste gate output, so the likeliest place for a real
credential to land by accident.

Rejected again: a `--baseline-path` baseline, on TASK-0011's original grounds (a careless
regeneration silently swallows a real leak). A fingerprint file has no regeneration step; every
line is added by hand, which means someone looked at the finding.

### Two mechanics that will cost you an hour if you miss them

1. **The file goes at `backend/.gitleaksignore`, not the repo root.** `--gitleaks-ignore-path`
   defaults to `.` — the current working directory — and `backend/scripts/ci.ps1:49` does
   `Push-Location $backendRoot` before the gate runs. A root-level file is read by nothing: the
   gate stays red and looks unfixed. Either put it in `backend/`, or pass `-i` explicitly and say
   why in this card.

2. **These fingerprints carry a commit sha, so they cannot rot.** Commit content is immutable, so
   an entry can never drift onto different content or mask a finding it was not written for. That
   guarantee holds ONLY in git mode. If the scan ever moves to `--no-git` or the newer `dir`
   command, fingerprints lose the commit field and become `file:rule:line` against mutable
   working-tree content — an entry could then suppress a real secret that happens to land at the
   same path, rule and line. **TASK-0016 rewrites these gate scripts**, so put a comment at the
   top of the ignore file stating that the entries must be re-derived if the scan mode changes.

## Implementation record (2026-09-04, backend-dev)

**Mechanism:** `backend/.gitleaksignore`, five fingerprint-pinned entries exactly as listed above
(verified byte-identical by re-running `gitleaks detect --source . --config .gitleaks.toml
--redact --no-banner -v` from `backend/`). Each entry carries its own comment naming the file and
why it's a fake credential, matching the standard of `.gitleaks.toml`'s `[[allowlists]]` comments.
A top-of-file comment states the git-mode-only immutability guarantee and instructs whoever
executes TASK-0016 to re-derive every fingerprint if the scan mode changes (`--no-git` / `dir`).

**Proof the rule still fires:** wrote a fresh, unrelated fake connection string
(`db7.internal-proof-only.example`, invented password, never committed anywhere) to a scratch file
in `$env:TEMP`, ran `gitleaks detect --source <tmp> --config backend/.gitleaks.toml --no-git
--no-banner --redact -v`, confirmed `RuleID: postgres-connection-string-with-password` fired,
`leaks found: 1`, exit code `1`. Scratch directory deleted immediately after. Note the project
config had to be passed explicitly — gitleaks' *default* ruleset (no `--config`) does not include
this project-specific rule, so a bare `gitleaks detect --no-git` on the scratch dir alone (first
attempt) found nothing; that's a gitleaks default-config fact, not something about the fix.

**A real credential newly pasted into `.agent/tasks/logs/` would still be caught:** verified with
`gitleaks protect --staged`, not `detect --no-git`, because that command scans exactly what a
commit would contain (the staged diff) without requiring an actual commit — `detect` in git mode
only sees committed history, so an untracked file is invisible to it, and creating a real commit to
prove the point would repeat this exact card's root cause. Staged a scratch file at
`.agent/tasks/logs/TASK-0017-verify-scratch.md` containing a differently-shaped fake credential at
a path/line no allowlist entry matches, ran `gitleaks protect --staged --source . --config
backend/.gitleaks.toml --redact --no-banner -v` from the repo root, confirmed both
`postgres-connection-string-with-password` and `generic-api-key` fired against it
(`leaks found: 2`), then `git reset` to unstage and deleted the file. No commit was created.

**Structural guard:** added one bullet to `backend/AGENTS.md` §5 (Definition of Done): if a task's
write-up quotes a credential-shaped string as proof of anything, the Secret scan gate must be
re-run *after* that write-up is finalized, not only after the code change, since the scanner reads
documentation along with code and a run taken before the write-up existed proves nothing about the
commit that ships. Chose this over a pre-commit hook (this repo has none yet, and adding the first
one is a bigger, separate decision than this card's scope) and over a `ci.ps1` ordering change
(the gate already runs last-committed-tree-wide; the actual gap was *when a human/agent re-runs it
relative to writing docs*, not the script's internal order).
