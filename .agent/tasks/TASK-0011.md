## Goal

`ci.ps1`'s Secret scan gate is red. It is red because TASK-0008 installed `gitleaks`, so the gate
executed for the first time in this repo's life — before that it printed `PASS: Secret scan` while
scanning nothing. Nine findings surfaced. **All nine were inspected by the orchestrator on
2026-08-27 and none is a real credential.** The gate must go green by fixing what is actually
wrong — an over-broad rule and an integrity hash mistaken for a key — not by disabling scanning.

## The finding

Gate invocation (`ci.ps1` line 251, run from `backend/`):
`gitleaks detect --source . --config .gitleaks.toml --redact --no-banner` → `leaks found: 9`.

Two families:

**A. `postgres-connection-string-with-password` — 5 hits, every one a documented placeholder.**
```
backend/README.md:51                                          Username=YOUR_USER;Password=YOUR_PASSWORD
backend/README.md:145                                         Username=...;Password=...
backend/src/SchoolManagement.Api/appsettings.Development.template.json:39   Username=<user>;Password=<pw>
backend/src/SchoolManagement.Infrastructure/Persistence/DesignTimeDbContextFactory.cs:24   (doc comment) Password=...
backend/ci/github-actions-backend.yml:111                     HISTORY ONLY — that path no longer exists
```
Root cause: the rule's regex (`backend/.gitleaks.toml:25`) is
`(?i)(host|server)\s*=\s*[^;"'\s]+;[^"']*password\s*=\s*[^;"'\s]{1,}` — it has **no `stopwords`
and no `allowlist`**, so `Password=...` and `Password=YOUR_PASSWORD` match as readily as a real
one. The rule was written 2026-08-03 and, because gitleaks was never installed, **has never run
until now**. It is untested, not wrong in intent.

**B. `generic-api-key` — 4 hits, all the SHA-256 contract hash.**
```
.agent/STATE.md:40, :58        openapi.json sha256: 228ae57f...
contracts/CONTRACT.lock:3      (x2 — current and an earlier commit)
```
A 64-hex integrity digest published on purpose. Not a credential in any sense.

**Note on history:** the gate scans git history by default, so 4 of the 9 (the moved workflow file,
the older `STATE.md` line, the earlier `CONTRACT.lock` commit) **cannot be cleared by editing
current files.** Any solution that only edits working-tree content will not turn this gate green.

TASK-0008's own guidance — "make the example obviously fake rather than adding an allowlist entry"
— was the right default but does not apply here: these examples are *already* obviously fake
(`YOUR_PASSWORD`, `...`, `<pw>`) and trip the rule regardless, and history is immutable.

  **Discovery that shaped the fix:** ran with `--redact=0` and read gitleaks' own source
  (`detect/detect.go`, `config/allowlist.go`) rather than guessing. This rule's regex has one
  capture group, `(host|server)` (present only to accept both keywords) — and with no `secretGroup`
  set, gitleaks uses "the first non-empty capture group" as `finding.Secret`. So every finding from
  this rule had `Secret` literally equal to the word `"Host"` or `"Server"`, never the connection
  string. `stopwords`, and the *default* allowlist target, both check against `Secret` unconditionally
  (`a.ContainsStopWord(finding.Secret)` — not affected by `regexTarget`). That means a Secret-scoped
  `stopwords` list, the card's first-listed option, **could not have worked for this rule** — it
  would have silently matched nothing while looking configured. It also explains why the file's
  pre-existing global allowlist entries (`ci_user`, `ci_password`,
  `Username=<user>;Password=<pw>`, `Password=\.\.\.`) had never suppressed anything for this rule
  either: same dead-on-arrival problem, present since 2026-08-03.

  **Family A fix:** a `[[allowlists]]` block with `targetRules =
  ["postgres-connection-string-with-password"]` and `regexTarget = "match"` (gitleaks' full regex
  match — the whole `Host=...;...;Password=...` string — sidestepping the broken `Secret`
  entirely), holding one tightly-anchored, case-insensitive regex per literal placeholder token:
  `YOUR_USER`, `YOUR_PASSWORD`, `<user>`, `<pw>`, bare `...`, bare `***`, plus
  `ci_user`/`ci_password` together (needed for the fifth, history-only finding in the old
  `ci/github-actions-backend.yml`). Rule-scoped, not path-scoped, per the card.

  **Family B fix:** chose the **path-scoped allowlist** over teaching `generic-api-key` about hex
  digests — reasoning recorded as a config comment and in `ASSUMPTIONS.md` §3.9: we don't own that
  rule's regex (`useDefault`), forking it risks drifting from upstream, and "64 hex chars is never a
  key" is false in general (some real keys are exactly that shape). `[[allowlists]]` with
  `targetRules = ["generic-api-key"]` and `paths` anchored to `contracts/CONTRACT.lock` and
  `.agent/STATE.md` only.

  **Structural note:** converted the file's one legacy `[allowlist]` table to the first
  `[[allowlists]]` entry (identical fields, identical global/no-`targetRules` behaviour) because
  gitleaks refuses to load a config mixing the singular and plural forms, and `targetRules` only
  exists on the plural form. Confirmed via `gitleaks/gitleaks` source
  (`config/config.go`: `"[allowlist] is deprecated, it cannot be used alongside [[allowlists]]"`)
  and its own `testdata/config/valid/allowlist_global_target_rules.toml` example, which this
  mirrors.

  Nothing was disabled, `--no-git` was not added, no severity threshold introduced — all three
  explicitly out of scope per the card, and not used.
