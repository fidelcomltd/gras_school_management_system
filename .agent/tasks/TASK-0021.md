# TASK-0021 — Cookie auth seam and the sign-in screen

Owner: frontend-dev
Depends on: TASK-0003 (contract), TASK-0020 (structure, form library, E2E harness)
Contract impact: none — consumes TASK-0003's contract, changes nothing
Status: queued

## Goal

An administrator signs in through the browser and lands in the back office. The provisional
bearer-token implementation is removed, not left dormant.

## The mechanism — not open for reinterpretation

**HttpOnly cookie session + CSRF token**, signed off by the human 2026-08-26 (CLAUDE.md §5,
`STATE.md ## Auth decision`). `frontend/src/lib/auth/` currently implements bearer-in-memory auth,
which is **known-wrong code carried deliberately** since 2026-08-26 awaiting this card.

The frontend holds no session token in JS at all — not in memory, not in `localStorage`. If any
part of this appears unworkable, stop and raise it. A carrier change needs human sign-off.

## Acceptance criteria

- [ ] `src/api/` regenerated from the **committed** `contracts/openapi.json` via
      `npm run generate:api`; `npm run check:api-drift` green. No hand edit to a generated file.
- [ ] `frontend/src/lib/auth/auth-session.ts` and the interceptors in `src/lib/http/http-client.ts`
      are rewritten to the cookie model. **The bearer implementation is deleted, not disabled.**
      `HANDOFF.md` records the change is confined to those two files — hold it there, and if it
      spreads further, say so rather than widening quietly.
- [ ] `credentials: 'include'` (or the axios equivalent) is set, and matches what TASK-0003
      actually configured for CORS, `SameSite`, `Secure` and domain. A mismatch is a blocker (§5)
      — prove it against the running backend, not by reading the config.
- [ ] CSRF token attached to every mutating request, implemented **once** in the API layer, never
      per-feature.
- [ ] **One refresh path, single-flight**: concurrent 401s queue behind one refresh attempt,
      implemented once in the API layer. A test drives two concurrent 401s and asserts exactly one
      refresh request goes out.
- [ ] **The idle window is extended ONLY by an explicit `POST /auth/refresh`** — ordinary
      requests do not touch it (`AdminSession.cs`, `AuthPolicy.IdleTimeout` = 30 min). So a user
      actively working for 31 minutes is signed out unless the app refreshes proactively. Since a
      reactive 401 is terminal by design (delta §3a), the proactive keepalive is the ONLY thing
      standing between an active user and a surprise logout. Build it, and test it.
- [ ] **The frontend never computes or assumes expiry from a hardcoded duration.** It reacts to
      401 and to the expiry the backend reports (§5). Grep your own diff for any duration literal
      near session handling before you claim this.
- [ ] Logout calls the server revoke endpoint, then clears client state. Clearing client state
      alone is a blocker (§5).
- [ ] Sign-in screen lives at `src/features/auth/`, per TASK-0020's convention, routed via
      `paths.*` in `src/app/router/paths.ts` — never a string literal.
- [ ] The form uses `react-hook-form` with a zod resolver (§7), including the field-level and
      form-level error states the API actually returns.
- [ ] **Playwright specs for the auth flow and one failure path** (§7 names auth first): a
      successful sign-in, and a rejected credential showing the error without leaking whether the
      email exists.
- [ ] `src/screens/scaffold-status/` deleted and `src/screens/` retired, with `/` routed to
      something real. Its drift entry is then struck.
- [ ] **TASK-0020's `e2e/smoke.spec.ts` asserts the scaffold-status heading "Foundation is in
      place" and the page title.** Deleting that screen breaks it BY DESIGN. Replace those
      assertions with equivalent ones against whatever now renders at `/` — do NOT delete the
      assertion to make the suite green. A spec weakened to keep passing is the defect family
      this project has spent four cards removing.
- [ ] `npm run verify` and `npm run check:api-drift` green, output pasted.
