## The signed-off mechanism — not open for reinterpretation

**HttpOnly cookie session + CSRF token.** Recorded in `STATE.md` `## Auth decision` with the
rationale in Decisions. The bearer-in-memory approach the frontend scaffold provisionally built
on 2026-08-03 is **superseded**; this card changes it.

The token itself does not change: spec 9.1's opaque 32-byte CSPRNG token, stored hashed
server-side, rotated on privilege change and on password change. Not a JWT. The cookie is only
the carrier.

If any part of this turns out to be unworkable, **stop and raise it** — do not switch carriers
mid-card. A carrier change needs the same human sign-off this one got.

## Goal

An administrator signs in with email and password and receives a session that the server can
revoke. The back office becomes usable by a real person instead of an anonymous caller.

## Contract delta

BREAKING. Draft the exact shapes into this card and get orchestrator approval **before**
implementing — §3 says contract changes are proposed, approved, then implemented, never
discovered afterwards. The surface is at minimum:

| Endpoint | Notes |
|---|---|
| `POST /api/v1/auth/sign-in` | Email + password. Sets the session cookie. Returns the current user, the effective privilege set, and the **backend-reported expiry** (the frontend must never compute expiry from a hardcoded duration). |
| `POST /api/v1/auth/sign-out` | Server-authoritative revoke, then cookie clear. |
| `GET /api/v1/auth/me` | Current account + effective privileges. Absorbs or replaces `/api/v1/reference/whoami` — decide which and say so; if it replaces it, that removal is part of the breaking change. |
| `POST /api/v1/auth/refresh` | Single-flight. |
| `POST /api/v1/auth/password` | Password change. Rotates the session token (spec 9.1). |
| CSRF token issue path | Whatever shape you propose — double-submit cookie or a fetched token. Justify the choice. |

Also part of the delta: the `401` vs `403` split (401 = not authenticated, 403 = authenticated
but unprivileged, generic body per TASK-0002), the lockout response shape and its error code,
and the security scheme declaration in the OpenAPI document.

## Acceptance criteria

- [ ] Argon2id password hashing, tuned to 150–300 ms per hash on the production instance, with
      cost parameters stored alongside the hash so they can be raised later without invalidating
      existing passwords (spec 9.1).
- [ ] Session tokens are 32 bytes from a CSPRNG, stored hashed server-side, and rotated on
      privilege change and on password change (spec 9.1).
- [ ] Logout is server-authoritative: revoke server-side, then clear client state. Clearing
      client state alone is a blocker (CLAUDE.md §5).
- [ ] One refresh path, single-flight: concurrent 401s queue behind one refresh attempt,
      implemented once in the API layer, never per-feature (CLAUDE.md §5).
- [ ] The frontend never computes or assumes expiry from a hardcoded duration; it reacts to 401
      and to the expiry the backend reports (CLAUDE.md §5).
- [ ] No token, password or pin appears in a URL, a log line, an error page or an analytics
      payload. Request logging redacts password and pin fields by name before writing (spec 9.1).
- [ ] Lockout per spec 6.1.11.
- [ ] Bootstrap: the first admin exists per spec 6.1.6.
- [ ] At least one active Super Admin exists at all times, enforced by the system (spec 4.1).
- [ ] Privilege escalation prevention per spec 6.1.7.
- [ ] CORS, `SameSite`, `Secure`, domain and credentials mode are configured as one coherent set
      end to end (CLAUDE.md §5). A frontend sending `credentials: 'include'` against a backend
      not configured for it is a blocker, so prove it with an integration test, not by reading.
- [ ] CSRF token required on every mutating request, implemented once in the API layer, never
      per-feature. A mutation without a valid token is rejected.
- [ ] The frontend holds no session token in JS at all — not in memory, not in `localStorage`.
      `frontend/src/lib/auth/auth-session.ts` and the interceptors in `src/lib/http/http-client.ts`
      are rewritten to the cookie model; the bearer implementation is removed, not left dormant.
- [ ] No second factor (spec 9.1, Appendix A entry 5) — an accepted limitation, not an omission.
