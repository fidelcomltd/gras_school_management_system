## The signed-off mechanism — not open for reinterpretation

**HttpOnly cookie session + CSRF token.** Recorded in `STATE.md` `## Auth decision` with the
rationale in Decisions. The bearer-in-memory approach the frontend scaffold provisionally built
on 2026-08-03 is **superseded**; TASK-0021 changes it.

The token itself does not change: spec 9.1's opaque 32-byte CSPRNG token, stored hashed
server-side, rotated on privilege change and on password change. Not a JWT. The cookie is only
the carrier.

If any part of this turns out to be unworkable, **stop and raise it** — do not switch carriers
mid-card. A carrier change needs the same human sign-off this one got.

## Goal

An administrator signs in with email and password and receives a session the server can revoke.
The back office becomes usable by a real person instead of an anonymous caller.

## Scope boundary — read this before planning

This card was split on 2026-09-05. It owns **authentication and sessions only**. Admin account
management (create, list, edit, deactivate), the super-admin invariant and privilege-escalation
prevention moved to **TASK-0019**, which also builds the idempotency substrate.

The split exists for one reason: creating an admin account is a retry-duplicable mutation, so it
fires the deferred-idempotency trigger (`STATE.md ## Known drift`, TASK-0013). Nothing in THIS
card does — a repeated sign-in makes a new session, a repeated sign-out and refresh are naturally
idempotent, and a repeated password change fails on the second attempt because the old password
no longer matches. **Therefore no `Idempotency-Key` work belongs here.**

That holds only while bootstrap stays off the wire:

- [ ] **The first admin is created by a seeded migration or a CLI/one-shot task, NOT an HTTP
      endpoint** (spec 6.1.6). An HTTP bootstrap endpoint would be retry-duplicable and would fire
      the trigger inside this card. If you conclude the spec requires an endpoint, **stop and say
      so** — that is a re-plan, not a judgement call you make while implementing.

## Acceptance criteria

- [ ] Argon2id password hashing, tuned to 150–300 ms per hash on the production instance, with
      cost parameters stored alongside the hash so they can be raised later without invalidating
      existing passwords (spec 9.1).
- [ ] Session tokens are 32 bytes from a CSPRNG, stored hashed server-side, and rotated on
      privilege change and on password change (spec 9.1).
- [ ] Logout is server-authoritative: revoke server-side, then clear client state. Clearing
      client state alone is a blocker (CLAUDE.md §5).
- [ ] One refresh path, single-flight: concurrent 401s queue behind one refresh attempt,
      implemented once in the API layer, never per-feature (CLAUDE.md §5).
- [ ] The expiry the backend reports is in the `sign-in` and `me` responses, so the frontend
      never has to compute one (CLAUDE.md §5). The frontend half is TASK-0021.
- [ ] No token, password or pin appears in a URL, a log line, an error page or an analytics
      payload. Request logging redacts password and pin fields by name before writing (spec 9.1).
- [ ] Lockout per spec 6.1.11.
- [ ] Bootstrap: the first admin exists per spec 6.1.6, created off the wire — see the scope
      boundary above.
- [ ] CORS, `SameSite`, `Secure`, domain and credentials mode are configured as one coherent set
      end to end (CLAUDE.md §5). A frontend sending `credentials: 'include'` against a backend
      not configured for it is a blocker, so prove it with an integration test, not by reading.
- [ ] CSRF token required on every mutating request, implemented once in the API layer, never
      per-feature. A mutation without a valid token is rejected.
- [ ] **`sign-in` AND `password` are both rate-limited under `RateLimitingOptions.SensitivePolicyName`,
      each with a test that proves rejection.** `sign-in` is the drift trigger from TASK-0015
      review: the sensitive policy is registered but has never had a user and no test anywhere
      asserts a 429. `password` is added per orchestrator approval 2026-09-05 — `currentPassword`
      is an online guessing surface too. Login/password rate limiting is a brute-force control,
      so it ships with a rejection test or it does not ship. `HealthRateLimitTests` is the
      pattern to copy.
- [ ] **`IEffectivePrivilegeProvider` gets a real implementation, replacing
      `NullEffectivePrivilegeProvider`, scoped to the super-admin flag path only** (§1,
      human-ratified 2026-09-05): `is_super_admin` ⇒ one `PrivilegeGrant` per privilege in the
      immutable register, `SchoolWide`, `SessionId: null`; every other account still resolves to
      `[]` until TASK-0019. No `role`/`role_assignment` persistence in this card.
- [ ] No second factor (spec 9.1, Appendix A entry 5) — an accepted limitation, not an omission.
- [ ] `./backend/scripts/ci.ps1` green with the integration suite RUNNING (`Skipped: 0`).
- [ ] `contracts/openapi.json` regenerated via `generate-openapi.ps1 -Promote`, `CONTRACT.lock`
      updated, and the new hash reported.
