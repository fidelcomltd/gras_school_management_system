- 2026-08-26 Client generator: **openapi-typescript, types only** (Open question 6). Rejected openapi-fetch / NSwag / Kiota because the frontend already owns a working axios transport with auth interceptors and a single-flight refresh seam (`src/lib/http/`); a runtime client would duplicate it and force a rewrite of that seam. `src/api/` holds generated types plus a thin typed request helper over that transport, which satisfies §7's "all server communication goes through `src/api/`" without running two HTTP stacks.

- 2026-08-26 Build sequencing departs from `index.md`'s suggested order in one place: the privilege register and authorisation middleware (TASK-0002) come **before** school settings, not after. Spec 9.2 requires every route to declare the privilege it needs and to fail registration at boot if it does not — building settings endpoints first would mean writing routes against an enforcement layer that does not exist, then retrofitting it.

- 2026-08-26 **Auth carrier: HttpOnly cookie session + CSRF token** (Open question 8), human sign-off per §5. Rejected the bearer-in-memory approach the frontend scaffold provisionally built: a token held in JS is readable by any XSS, and it dies on page reload, so it must either sign the user out on refresh or be persisted somewhere — which is exactly the exposure the in-memory choice was trying to avoid. The cookie carries the same opaque server-side token spec 9.1 mandates, so nothing about the backend token model changes. Cost is a CSRF token on every mutation and one coherent cookie/CORS configuration end to end; the frontend change is confined to `src/lib/auth/auth-session.ts` and `src/lib/http/http-client.ts` per `frontend/HANDOFF.md`.

- 2026-08-26 ~~OpenAPI generation is not deterministic between incremental and clean builds.~~ (ORCHESTRATOR OVERSTATED THIS — the real trigger is narrower: a document modified outside the generation target. Ordinary pulls and branch switches self-heal. See TASK-0010's closing Log.) **FIXED
  by TASK-0010, moved to `review`.** Root cause found by reading
  `Microsoft.Extensions.ApiDescription.Server`'s own `.targets`: the `GenerateOpenApiDocuments` MSBuild
  target is `Inputs="$(TargetPath)" Outputs="$(_OpenApiDocumentsCache)"` — an up-to-date check between
  the compiled assembly and one bookkeeping file in `obj/` (`SchoolManagement.Api.OpenApiFiles.cache`).
  It never inspects the generated document itself, so if the document is modified by anything other
  than that target running — a hand-edit was the reproduced case — while the assembly and cache file
  stay as they were, the target is (correctly, by its own contract) skipped, and the modified document
  survives untouched while `generate-openapi.ps1` still prints `==> Generated:`.
  **Checked the honest caveat before sizing the fix**: a real edit to `OpenApiExamples.cs` (even a
  no-op comment) reliably self-heals a corrupted artefact on the next incremental run, because a real
  source change advances the assembly's timestamp past the cache file's and forces the target to rerun
  — so branch switches and normal source edits are not a trigger. `ci.ps1`'s two builds (plain Build
  gate, then the flagged Generate gate) do not interfere either — traced and confirmed live: the cache
  file doesn't exist yet when the first flagged build of a run starts, so that target always runs
  unconditionally the first time, every time. **The only trigger found was a document changed outside
  the generation target** — hand-edit reproduced exactly per TASK-0009's original repro table
  (25807 bytes / sha `6a5d51fe...` on corruption, `228ae57f...` restored); an interrupted build is a
  plausible sibling of the same class, not separately reproduced, and the fix covers it regardless.
  **Fix**: `backend/scripts/generate-openapi.ps1` now deletes both the generated document and
  `src/SchoolManagement.Api/obj/SchoolManagement.Api.OpenApiFiles.cache` before every `dotnet build`
  call. Deleting the cache file is what matters — it is the target's actual tracked `Outputs`, so
  removing it makes regeneration unconditional every run. Deleting the artefact alone was tested and
  proven insufficient first: the target still skips on the cache-file check alone, so no document gets
  written and the script's own `Test-Path` guard throws — which is what led to targeting the cache file
  instead. Verified fixed with the identical hand-edit-then-incremental-build sequence:
  now yields `228ae57f...` (matching the committed contract) even without touching `obj`/`bin`, and
  twice in a row to confirm it isn't a one-off. `-Promote` never run while verifying; committed contract
  hash unchanged throughout. Full findings, evidence and the `ci.ps1` gate output are in TASK-0010's Log.

## Why CLAUDE.md §13 exists — rationale, measured 2026-09-04

§13 in the root CLAUDE.md is deliberately terse, because it is loaded by every agent session and
a section about saving tokens that costs 900 tokens per dispatch is self-defeating. The reasoning
behind each of its rules is here instead.

**The measurement that prompted it.** Before the restructure, the fixed cost of one `frontend-dev`
dispatch — loaded before it read a single line of application code — was about 25,000 tokens:
CLAUDE.md 18.5 KB, `STATE.md` 36.3 KB, `contracts/openapi.json` 25 KB read whole for a document
describing four endpoints, `frontend/CONVENTIONS.md` 13.9 KB, and a task card averaging 7 KB.
That cost was paid again in full on every re-dispatch after a failed gate. After the restructure
the same dispatch loads about 9,500 tokens.

**Why the old ledger cap failed.** §4.1 capped `STATE.md` at "~200 lines". The file sat at exactly
200 lines and reported green while carrying 36.3 KB, because `## Decisions` held 10.3 KB in 18
lines and `## Known drift` held 14.7 KB in 27 lines — an average of 550 bytes per nominally
one-line entry, with one line reaching 2,345 bytes. A line cap does not bound cost. The cap is
now on bytes, and the sections are indexes pointing at full text in `decisions/` and `drift/`.

**Why lazy loading rather than deletion.** Nothing was deleted in the 2026-09-04 restructure; all
19 drift entries, 11 decision entries, the closure narrative, the nine resolved open questions and
eight task-card logs were moved to archives and indexed. Quality is not protected by an agent
having read everything — it is protected by §4.4's mechanical drift checks, which are unchanged.
Small contexts are safe precisely because the gates, not an agent's memory, catch mistakes.

**Why a skipped suite is the most expensive defect on record.** TASK-0002 was reported done twice
on runs whose integration suite silently skipped; run for real it failed, on a defect that had
already reached the committed contract. Each false close cost a full re-dispatch of a Sonnet
session plus an orchestrator review. No file-size saving in this repository comes close. Hence the
rule, and hence TASK-0016, which makes `ci.ps1` exit non-zero on `Failed > 0` and on `Skipped > 0`.

**Why §6 and §7 moved but kept their numbers.** 142 references to "§6" and "§7" exist across 24
files. Renaming them was rejected as a large, low-value, error-prone diff. The bodies moved to
`.agent/spec/backend.md` and `.agent/spec/frontend.md`; §6 and §7 remain in CLAUDE.md as pointer
stubs, so every existing reference still resolves. `backend/AGENTS.md` and
`frontend/CONVENTIONS.md` were checked for duplication and found to be concrete recipes
implementing the specs rather than restatements of them, so both were left in place.

## 2026-09-04 — TASK-0012 and TASK-0017 closure notes

**TASK-0012 — problem-detail extension members.** The contract declared `additionalProperties: false`
on both problem schemas while every error response carried `errorCode` and `traceId`, so each
schema's own `example` was invalid against the schema illustrating it, and a five-member
`ProblemDetails` had already reached `frontend/src/api/schema.d.ts`. Both members are now declared
with the schemas left CLOSED — declaring them inside `additionalProperties: false` keeps the
closed-type discipline that is right for request bodies while making the two members clients are
told to depend on part of the contract. `UnmappedMemberHandling.Disallow` was left global; the fix
is a targeted `IOpenApiSchemaTransformer`.

**The `required` decision, corrected mid-card.** The orchestrator initially told the human both
members would be `required`, then read the code and found that false for `errorCode`: `traceId`
comes from the single central `CustomizeProblemDetails` hook (`Program.cs`), so it is on every
problem response including framework-produced ones, but `errorCode` is attached only in
`Http/ResultExtensions.cs` and `Http/GlobalExceptionHandler.cs` — a model-binding 400 or a 401 from
authentication middleware carries none. Marking it required would have declared something the API
does not always send, i.e. the same class of contract lie the card existed to remove. Shipped as
`traceId` required, `errorCode` optional with its absence documented in the schema description.
Consequence worth remembering at TASK-0003: every frontend error branch needs an
`errorCode`-absent fallback, because middleware 401s are exactly that case, and one of the two new
frontend tests pins it.

**A latent bug the card did not predict.** `frontend/src/lib/http/http-error.ts` held a
hand-duplicated `ProblemDetails` interface, and `ApiError.code` was sourced from `problem.type` —
the RFC type URN, not the error code — so any future branch on `.code` would have matched the wrong
field entirely. Now a type alias of the generated schema, with `ApiError.errorCode`/`traceId`. This
is the argument for §3's "one source of truth" in miniature: the duplicate drifted silently because
nothing compared it to the contract.

**Two new contract tests, one of them general.**
`EverySchemaExample_ValidatesAgainstItsOwnSchema` checks every schema in the document, not just the
two: under `additionalProperties: false` no example may carry an undeclared member, and every
required property must appear. `EveryOperation_DocumentsItsErrorResponses` had not caught this. The
new tests were proven real by running them against the pre-fix document and watching them fail.

**TASK-0017 — why it existed at all.** Not a security finding. TASK-0011 proved its narrowed
gitleaks rule still fired by quoting the fake connection string it had tested with into its own
card, its run log, and `ASSUMPTIONS.md`; committing that write-up re-armed the rule against its own
documentation. Full mechanics, the rejected alternatives, and the two silent failure modes are in
the `## Known drift` archive entry for 2026-09-04 and at the head of `backend/.gitleaksignore`.

**Escalation calibration, recorded because it changed how the orchestrator works.** The orchestrator
escalated the TASK-0017 mechanism choice to the human on the strength of the 2026-08-27 precedent
